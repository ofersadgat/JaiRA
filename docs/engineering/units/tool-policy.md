# Tool policy

## The unit decides what a tool call may do and where, and leaves remembering and asking to others

- `command.ts`: `takeApart(line, dialect)` turns a line into the requests it is made of, in the `posix` or `powershell` dialect ([0007](../decisions/0007-permissionSets.md) §4): every command, every redirect, and every piece it could not model, each with its span in the original line. It comes apart at `&&`, `||`, `;`, `&`, `|`, newlines, `( … )`, `{ … }`, `$( … )`, backticks and `<( … )`; a here-document's body is data; `if`, `then`, `do` and `!` lead a command without being one. Embedders are opened recursively, with spans kept in the original line through a per-character offset map: `sh -c`, `powershell -Command`, `eval`, `exec`, `find -exec`, `xargs`, `env`, `sudo`, `nohup`, `time`, `timeout`, `nice`, `watch`, `parallel`, `ssh`, `docker exec`, `git -c alias.…`, `git submodule foreach`, `npx`, `pnpm dlx`. It skips the value a `-C` or `-c` flag takes, as in `git -C <dir>`. `parseCommand` is the same walk reported as `ParsedCommand`s. A line it cannot model comes back `unparsed` with a reason, an unreadable payload comes back as a request of kind `unparsed` beside the rest, and it never throws.
- `shellTables.ts`: the shell's tables, as data: `EMBEDDERS`, the utility → standard-tool tables `POSIX_UTILITIES` and `POWERSHELL_UTILITIES`, `NO_REQUEST`, `NULL_DEVICES`, `SCRIPT_INTERPRETERS`, `SCRIPT_RUNNERS` and `SCRIPT_EXTENSIONS`.
- `commandParts.ts` in runtime: `classifyRequest` names what a request is for: a standard tool on its paths or url, `script`, a command subject, or nothing. `shellPermissionSetOf` and `shellPermissionSetOfBlock` read a `Permission set` or a lowered block as the map a line is judged against — a block's `subjects` and `source`, which a run's block carries too since upstream passes a host's keys through; a block with no `subjects` has no map — and `lookUp` answers for one part: the most specific command entry naming the program, then the part's own subject, then `other`, then `ask`.
- `commandParts.ts` in shared: the payload, `CommandApproval` and `CommandPart`, with `askingParts`, `entriesToRemember` and `chosenWidths`. `CommandApproval.permissionSet` names the permission set that judged the line: the reference a state names it by, or `inline`.
- `permissionSetEdit.ts` in shared: "add to the permission set" as text in, text out. `addToPermissionSetText` sets entries in a permission set map, replacing a value where it stands, only the `mode` of an entry written as an object, and adding a new subject as one line after the last; `overridePermissionSetText` writes a new file that starts from a lower layer's by an explicit root and refuses a bare `$`; `permissionSetTextFollows` and `describeAddition` read one.
- `policy.ts`: `decideCommand(policy, line, dialect, options)` judges every part of a line and keeps the strictest verdict, returning the parts beside it. The narrowing decides a line once, under the map the state's block carries, or under the permission set the policy was compiled for when the block carries none. Per part: a `.jaira/` path denies; then, unless `functions.bash.builtins` is off, the built-in denies for destructive git and `rm -r .git`, then the built-in asks for push, merge, network programs, publishing, installing, deploying and credential paths, and otherwise `default`, which allows; then the permission set's answer, the stricter of the two kept, except that an entry naming the program replaces a built-in ask or the default — an entry that names a FUNCTION answers `function`, ranked between `allowed` and `asks`, and the part's `decidedBy.function` says which; a part the parser cannot vouch for asks at least; an answer remembered in `CommandGrants` settles a part that asks; and a scope table answers for the part's place by the standard tool the part is. `CommandGrants` keeps answers by width, never by line. `JairaPolicy` is `{ builtins?: boolean }` and nothing else, read off `functions.bash.builtins` by `projectPolicy(config)`. `compilePolicy(policy, options)` turns it into upstream `ExecPolicy`, folding the per-tool modes of `options.permission set` into `baseline.tools`: `bash`, `run_command` and six other command tool names get upstream's `smart` in the baseline (a state that declares no permission set is judged by it), a permission set's shell folds over it as `ask`, no other tool gets a mode or a default from the project, `show_artifact` gets a size-judging approver that nothing resolves to since the project policy's `tools` went, a path under `.jaira/` is denied, and `scopeOf` narrows each call by the executor floor and the calling state's `permissions.scopes`, and for a command tool also by the line's own verdict: a deny always, an ask when a permission set is judging the line (a line a permission set judges is audited here, whatever it came to). For a call that is not a shell line, the narrowing notes against its input which function decides it, when its line (or `other`) names one in the block's `functions` (`functionCallOf`). The decision is kept against the call's input object, where the `smart` approver and `commandDecisionOf` find it again. `commandNarrowingOf` hands `gateTools` the line half alone. `policyCanEscalate` says whether a person could ever be asked.
- `approval.ts`: `ApprovalHub` parks an `ask` as an `ApprovalRequest`, which carries the decision's `parts` when the call was a shell line. `grants(taskId)` is the run's `CommandGrants`, emptied by `allow(taskId)`; `decide(requestId, decision, scope, remember, why)` stores the asking parts at the chosen widths and then answers upstream `once`, and keeps a `deny`'s `why` against the call's input, where `refusalOf(input)` finds it: upstream's own refusal says only "denied by permission policy". `approver({ taskId, functions })` is `withPermissionFunctions` over the park, so every host that parks approvals — the app's runs and turns, and a CLI run's terminal — asks the functions first and lets a line its parts allow through.
- `permissionFunctions.ts` in runtime: a permission set line that names a FUNCTION ([0007](../decisions/0007-permissionSets.md), amended 2026-09-22). `withPermissionFunctions(approve, options)` is the approver a host hands the engine: a line the narrowing allowed runs and one it denied is refused without anybody asked; each part whose verdict is `function` is put to its function in order, the first `deny` refusing the line; what still asks reaches `approve` with the answered parts on the request (`setCommandDecision`); a tool call `functionCallOf` names is put to its function; a function that cannot answer leaves the part asking with its reason (`noteApprovalReason`). Every function answer is `once`. `permissionFunctionState(reference)` is the one state a function runs as (its output calls the reference with `.inputs.request`, or is an expression document), and `permissionFunctionRunner({ load, registry, prompt })` runs it through the engine and reads `allow` or `deny`. `registerApprovalPrompt(registry, park)` registers `approve_tool_call`, parked on the host's gate hub and answered `{ decision }` (a seeded answer names the request it answered, and another request asks again). `registerSmartFunction(registry, { prompt, config })` registers `smart`: `smartJudgeOperation` with `functions.smart.model` and `functions.smart.prompt`, and `unsure` put to the approval prompt. `registerPermissionFunctionSignatures` declares both for the loader (`hostCalleeSignatures`).
- `runPolicy.ts`: a run's policy, one recipe for every host that starts a run. `compileRunPolicy(config, { workspaceRoot, onDecision, grants })` is `compilePolicy` over `projectPolicy(config)` with the executor floor `scopeFloorOf` reads off the executor tree, the workspace, `artifacts.askAboveBytes` and the run's `CommandGrants`. `securityFloorOf(config, root)` is that floor compiled into Claude rules as a prompt executor's `securityFloor`. The app's `startRun` and every CLI run call both; only who answers an ask, and where the audit lands, differ.
- `commandApprover.ts` in the CLI: a CLI run's approver ([cli](cli.md)). `governRun` is `compileRunPolicy` with `policyAuditRow` into `command_log` and an `ApprovalHub`'s approver. At a terminal the hub puts one request at a time to the person, drawn as the app draws it — the line, its parts numbered under it, the matched words marked, a row per part with subject, verdict and decider — and answered once, for this run at the asking parts' widths, or not. With nobody to ask it refuses each request with `unattendedRefusal`, which names why nobody was asked and, per asking part, what would answer it for good: the permission set line where a permission set judged the part or where a permission set is judging a line a built-in asked about, `functions.bash.builtins: false` where a built-in asked about a line no permission set judges (`run_command`'s, or a state's that declares no permission set), nothing where the parser could not read it.
- `tools.ts`: `gateTools` wraps named registry tools and builds a `ToolGate` over one `PermissionLedger` for one conversation turn; it reads modes from a `PermissionSet`, the one it is handed or the one it reads back from `names` and the lowered `authored` block, writes the block the upstream gate takes from that map, and seeds no profile and registers no profile table. `grantAlwaysGrantedTools` adds `show_artifact` to every prompt state of a run's resolved bundle. `claudeReplacements` reads upstream's `replacesNative` map off the claude declaration. `scopeNarrowingFor` and `commandSubjects` build the per-call narrowing, and `partScopeFor` answers for one part of a line by the standard tool it is. `compileClaudeScopeRules` and `claudePermissionSettings` compile a scope table into Claude Code permission rules, one rule for every native of a standard tool. `createRunCommandFunction` builds `run_command`, which gates itself, and fails a refused line with `command refused: ` and the policy's reason for the line (`commandDecisionOf`) and the approver's for the refusal (`refusalOf`), upstream's sentence only when neither said anything.
- `agentTools.ts` in runtime: what an agent is handed ([0007](../decisions/0007-permissionSets.md) step 2). `CLAUDE_TOOLS`, `CODEX_TOOLS` and `GENERIC_CLI_TOOLS` are the executors' declarations, in the shape [agent-executors](agent-executors.md) describes. `planAgentTools(permission set, declaration)` resolves a permission set against one declaration into `inject`, `displaced`, `askNatives`, `denyNatives` and `switches`. The built-in of a standard tool the permission set does not hold is removed. `viewOfPermissionSet` reads a permission set in hand and `viewOfServices` reads one back off what the engine hands an executor, or answers `undefined` when the block carries no `PERMISSION_SET_MARKERS` — a state that declares no permission set: membership off `ctx.tools`, and what was written off `ctx.authored`, the state's resolved block, through `permissionSetOfEnvironment` — whose code each held tool chose, a written `other`, and the shell's authored mode from `subjects` — with `ctx.gate` answering where the block says nothing. A switch is on exactly when the plan KEEPS a native it unlocks (a subject held with `implementation: "native"` and not denied): a subject held with ours is served and gated, and a shut switch is how a coarse transport's native is displaced. `withAgentPermissionSet(declaration, executor, options)` hands a call whose state declares no permission set to the executor untouched, and otherwise applies the plan to one prompt call: for a `tools` transport it names the removed and displaced natives in a copy of `ctx.policy.baseline.tools` and answers `deny` for them from a copy of `ctx.gate`, which is where the upstream executor builds `disallowedTools` from, writes the kept natives into `providerOptions.claudeCode.settings.permissions.ask`, takes a tool whose entry chose `native` out of the copy of `ctx.tools` it hands on so ours is not injected beside the kept built-in, and asks the gate about a native by its standard name with `file_path` copied to the standard tool's path argument; for a `switches` transport (codex) it picks the executor for that setting of the switches and hands it the held tools of ours to serve over its MCP bridge, less any whose entry kept codex's own, with a copy of the policy whose baseline names only those served tools (`switchedServices`) — codex has no deny list and refuses one, and the switch is where the permission set's removals reach it; the gate is untouched, and upstream puts every call that crosses the bridge to it before the tool runs; for `none` it refuses a permission set that denies anything. `agentFunctionWrapper(declaration, label)` is that same wrapper as the `wrapExecutor` upstream's function entry takes, so a claude agent reached as a FUNCTION is held by the route's own code: an entry that says `native` keeps the built-in under an ask rule written into the op the entry builds. `holdAgentFunction(declaration, run, label)` holds the two agents whose holding reads a function call's inputs: codex by writing `permissionMode: "plan"` (its `--sandbox read-only`) over the call's own where the permission set leaves the writing switch off, served its held tools as the route serves them, and a generic CLI by refusing a permission set that denies anything; it throws for a `tools` transport. `PERMISSION_SET_SERVICE` and `withPermissionSetService` are how a caller that knows its permission set publishes it on the services bundle.
- `agentTools.ts` in shared: `AgentToolDeclaration` (`channel`, `natives`, `switches`) and the pure questions asked of one, `standardOfNative`, `nativesOfStandard`, `primaryNativeOf`, `unmappedNatives` and `replacementsOf`.
- `permissionSets.ts` in shared: the permission set, the one map every reader of a grant and its modes consumes ([0007](../decisions/0007-permissionSets.md) step 1). `PermissionSet` is `entries` (subject → `{kind, mode, implementation, offered}`) and `other`; it has no profile. `parsePermissionSet` reads the authored map and reports a bad mode as an error and an unknown tool name as a warning. `resolvePermissionSetDecl` follows a bare-string reference and `$ref` with sibling overrides through an injected reader, and names a cycle. `offeredTools`, `toolModes`, `toolImplementations` and `shellSubjects` are what consumers read. `offeredTools` is what is handed to somebody, the list lowering writes and the set an agent plan calls held, so it leaves out a tool marked `unserved`; `holdsTool` and `heldTools` are what a person reads and counts, and count an unserved tool by its entry alone, because a lowered block read back has it un-offered. `declOfPermissionSet` writes a permission set back out as the map an author would write: held lines only, an implementation only where it is `native`, a line with no mode as `ask`, and `other` always. `gateToolModes` is `toolModes` as the gate takes them: a function as `ask`, and the shell's entry as `ask` whatever it says, which is how `bash` is lowered; its authored mode is carried in `subjects`, and `permissionSetOfEnvironment` puts it back. `shellWithheld` says when a map's shell is held and handed to nobody: its entry is `deny` and no command subject or `script` allows, asks or names a function. Such a shell is left out of `offeredTools`, `gateToolModes` answers `deny` for it, and it reads back as held. `permissionsOfPermissionSet` writes `implementations` on every map, `{}` where every held tool is ours, so the engine's per-key merge of `permissions` replaces a parent's choices instead of carrying them into a child that wrote a permission set of its own; it writes the two `PERMISSION_SET_MARKERS` entries, `jaira:toolset+` as `allow` and `jaira:toolset-` as `deny` (the keys keep that spelling), into the `permissions.tools` of every permission set, so a lowered map can be told from a state that declares none; it writes `functions` — subject → reference, empty when no line names a function — on every map too, so a child's map never inherits its parent's function; `isLoweredPermissionSet` reads them, `isPermissionSetMarkKey` names them, and every reader of `permissions.tools` skips them. `permissionSetOfEnvironment` reads a lowered block back: a listed tool at its `permissions.tools` mode, a mode for a tool the list does not offer as an un-offered entry (a withheld shell, an unserved tool, or a key a child inherited), and `other`, `subjects` and `implementations` as they were, with every subject `functions` names back as that function. `lowerStatePermissionSets` rewrites a map-form state into the `tools` list and `permissions` block the upstream engine takes, in a state's `environment`, its `operation` and each child mount's `environment`. A block that is itself a reference (`"$/lib/env"`, or `{ "$ref": …, …siblings }` with no `tools` of its own) is opened: `expandedFields` follows it through the reader, down every reference its target starts from, to the `tools` and `permissions` it holds once expanded — nearest `tools` whole, `permissions` per key, as upstream's `$ref` merge does — and a permission set there is lowered from the target's file and written BESIDE the reference as sibling `tools` and `permissions`, which upstream's merge lets replace the target's map; the reference stays, so the target's other fields and relative references keep their meaning, and a referenced block with no permission set, or one the reader cannot follow, is left alone. It returns a state with no permission set as the same object, asks an injected `checkFunction` about every function a permission set names — an unresolvable one is an error at its entry — and reports as errors the list form of `tools` (written, or in a file a reference names) and a `permissions` block that says `tools`, `default`, `other` or `profile`. `permissionSetOfSettings` reads a message's `permission set`, which is what the composer writes, or the lowered list and block a state's own declaration arrives as.
- `permissionSetBuckets.ts` in shared: buckets, and which permission set a map is ([0007](../decisions/0007-permissionSets.md) steps 4 and 5). `PermissionSetChoice` is one permission set a card can offer: its id, bucket, name, layer and resolved map. `permissionSetSignature` reduces a permission set to what it says: its held lines with mode and implementation, sorted, and `other`, with a tool the caller does not register left out. `samePermissionSet` and `matchPermissionSet(current, choices, bucket, registered)` compare signatures, and a map that holds nothing matches nothing. `bucketOf` finds the bucket a conversation opens on by the same match, `chat` tried first and answered when nothing matches. `permissionSetBuckets` lists the hierarchy with each bucket's layer and hint, `permissionSetsOfBucket` orders a bucket's rows, and `permissionSetLabel`, `permissionSetHint`, `permissionSetGlyph` and `permissionSetSummary` word a row: the shipped files' words are a table in this file, and anybody else's permission set is its file name over a count of its lines. `permissionSetNameProblem` and `permissionSetBucketProblem` say what is wrong with a name a file or a folder cannot have.
- `builtin/permission-sets/` in shared: the eight files that ship, `chat/{ask-first, read-only, auto, full}.json` and `chat_control/` with the same four names. The `chat` four hold every tool a conversation can be handed, with the modes the composer's four presets wrote, and end in the `other` that preset gave a name it had never heard of: `ask`, `deny`, `{ "function": "smart" }`, `allow` — the `auto` preset's word `smart` is the shipped function of that name now, on every line of both `auto` files. The `chat_control` four hold only `list_workflows`, `start_task`, `move_task`, `list_tasks`, `answer_question`, `hold_task`, `release_task` and `stop_task`, with `other: "deny"`; its `read-only` allows `list_workflows` and `list_tasks` and denies the rest.
- `permissionSets.ts` in persistence: `loadWorkflowBundle` is `loadBundle` behind that lowering, used by the browser, the pre-run load, the digest, the state views and the CLI. `permissionSetReader` resolves a permission set reference with upstream `resolveReference` and the bundle's own options, so `$/permission-sets/<bucket>/<name>` searches `paths.roots` in order and the file reaches `onReferencedFile`. `listPermissionSets(roots)` lists `permission-sets/<bucket>/<name>.json` across the layer roots, first root winning, buckets free to nest. `readPermissionSets(paths)` reads each of them through `permissionSetReader` into a `PermissionSetChoice` with its layer and its map with references followed, and leaves out a file that does not resolve or does not parse.
- `toolVocabulary.ts`: `TOOL_SPECS`, the one table of standard tool names with category, `pathArgs`, `urlArgs`, `nativeOnly`, `alwaysGranted` and `unserved`. It holds no agent's native names, no `readOnly` and no profile. The category `tasks`, drawn as Tasks & workflows, holds the eight workflow tools of [0005](../decisions/0005-connect.md) §3, served since step 6 by `registerWorkflowTools`. `unserved` remains for a tool whose name is known before anything serves it: a permission set may hold such a name and the linter does not warn, and `offeredTools`, `planAgentTools` and `JAIRA_TOOLS` each skip it; `isServedTool` answers for one name. No shipped tool carries it now.
- `permissionSetEdit.ts` in shared and `addToPermissionSet` / `permissionSetWriteTargets` in persistence `permissionSets.ts`: "Add to the permission set" ([0007](../decisions/0007-permissionSets.md) step 3). A layer that holds the file gets the line added in place, byte for byte elsewhere; a layer that does not gets an override `{ "$ref": "$SYSTEM|$BASE/permission-sets/…", "<subject>": "<mode>" }` that keeps following the lower layer. Only a bare `$/permission-sets/<bucket>/<name>` reference is writable; lowering records which permission set a block came from as `permissions.source` (the reference, or `inline`), and the policy puts it on `CommandApproval.permissionSet`.
- `agentHanded.ts` in runtime: what a permission set does to an agent, MEASURED. `handedToClaude(environment)` runs a one-state workflow under one effective lowered block through the engine, `withAgentPermissionSet` and the upstream executor to the query options a real `claude` would be spawned with (a fake `AgentQuery` stands in for the binary alone), and reads off what is served, removed and pre-approved, and — by asking the spawn's own `canUseTool` — what decides a call by every name the agent can still address, the shell by one line per kind of part (`SHELL_PROBES`). Reach is judged, not mechanism: a way in that is refused is not a way in, and a shell every line of which is refused is not a shell. `handedToClaude` takes `via: "function"` to reach the same agent as `operation.function: "claude-cli"`. `handedToCodex` is its codex half, by a model prefix or as a function, through upstream's REAL codex transport — its refusals, its argv, its bridge — with a spawn double for the binary and a bridge double that records what it would serve: it reads the sandbox off the argv, the `mcp_servers.dai` override, the served tools, and what decides a call to each by calling it through the binding the bridge would run, the shell by `SHELL_PROBES`; with configured MCP servers, a connection double stands in for each, and `mcp` is what the gate the bridge puts a proxied call to decides for each of `mcpProbes`.
- `scopes.ts`: glob matching and `resolveScope`, `resolveUrlScope`, `resolveScopes`, `scopeModeOf` and `layeredScopeMode`. The most specific glob that says anything about the tool decides, an unmatched place is denied, and a call about several places takes the strictest answer.
- `operationVocabulary.ts`: `PERMISSION_MODES` (`allow`, `deny`, `ask`), `FunctionMode` and `PermissionSetMode` with `isFunctionMode`, `gateModeOf`, `sameMode` and `modeWord`, `SMART_FUNCTION` and `APPROVAL_PROMPT_FUNCTION`, `PermissionsDecl`, the block a permission set lowers to — `tools`, `other`, and the `subjects`, `source`, `functions` and `implementations` keys lowering writes, and `scopes`, the one key an author writes —, `ChatSettings` with its optional `permission set`, `ToolImplementation`, `ToolChoice` with the native name each agent route has for the tool, and `ChatPlanView.available` with the `permission sets` and the `bucket` the composer's Permissions card draws. The function presets are gone; `READ_ONLY_PRESET_TOOLS` is kept frozen for the tests that hold `chat/read-only` to the map the preset wrote. The same file holds the operation field tables the authoring form and the operation schema read.
- `commandLog.ts`: `CommandLog.record`, `list` and `summary` over `command_log`. In `service.ts`, `startRun` passes `compilePolicy` an `onDecision` that writes one row per decision, and `scopeFloorOf` reads the floor.

It deliberately does not own:

- Resolving a mode through the ledger, and escalating: upstream `decideToolCall`, `PermissionLedger`, `withPermission` and `createToolGate` in `@declarative-ai/permissions`. Upstream still has profiles; nothing JaiRA lowers carries one, and the linter refuses an authored one.
- Building `disallowedTools`, `allowedTools` and the permission callback from the services an executor is handed: upstream `AgentExecutor` in `@declarative-ai/agents-api`.
- Parking an approval for a person and attaching the policy's reason: [interaction-hub](interaction-hub.md). The inbox channels: [inbox-channels](../contracts/inbox-channels.md).
- Expanding every other reference in a state, merging `environment` layers, and resolving a lowered `tools` list against the registry: upstream `@declarative-ai/hw`. It reads a non-array `tools` as a binding and refuses a map with `unrecognized binding form`, which is why lowering happens before it.
- The tools themselves: [host-tools](host-tools.md) and [host-tool-vocabulary](../contracts/host-tool-vocabulary.md).
- MCP servers — configuring them, detecting the ones other tools run, probing their tools, and handing them to claude and codex (whose bridge proxies them, so a call to one of their tools is gated there as ours are): [mcp-servers](mcp-servers.md). What it does to a call to one of their tools is here, and is the shell's program groups again: a permission set line `mcp__<server>__<tool>` for one tool, and a SERVER line `mcp__<server>` for every tool of it no line names, answered in that order and then by `other` (`mcpModeOf`). The lines lower into `permissions.tools` at their gate modes; `translatedGate` asks the gate about a tool with no line of its own by its server's name and notes the tool on the call's input; the narrowing judges the call as one part of kind `mcp` whose widths are the tool and its server (`decideMcpCall`), so the approver, "for this run" and "add to the permission set" — a TOOL line by default — serve it as they serve a shell part.
- Parsing `functions` and executor `scopes`: [project-config](project-config.md), with the shapes in [settings-json](../contracts/settings-json.md). Folding the compiled floor over every prompt call: `withSecurityFloor` in [executor-tree](executor-tree.md).
- Deleting `command_log` rows: [history-pruning](history-pruning.md) and [task-lifecycle](task-lifecycle.md).

## The unit is core logic behind the upstream permission seams, compiled once per run and once per turn

- Layer `core`. The runtime and shared files import upstream packages, `@jaira/shared` and `paths.ts` from [process-exec](process-exec.md), whose `dialectFor` picks the parser dialect by the same rule `interpreterFor` picks the shell, so the language judged is the language run. `commandLog.ts` is persistence code and the wiring is main-process code.
- Upstream seams: `ExecPolicy` with `baseline`, `smart` and `scopeOf`, and `Approver`, reach the engine on the services seam as `ctx.policy` and `ctx.approve`. `ScopeNarrowing` is the `scopeOf` callback. `ToolGate` is what a delegated agent's permission callback consults. `providerOptions.claudeCode.settings.permissions` carries `allow`, `ask` and `deny` rules to Claude Code. `ExecServices.tools`, `ExecServices.gate` and `ExecServices.policy` are what `withAgentPermissionSet` hands the agent executor copies of, and with `ExecServices.authored` — the state's resolved `permissions` block, host keys included, published by the engine with or without an approver (declarative-ai 3f5e5cc) — what it reads a run's permission set back from. Upstream `literalPermissions` passes every key it does not read through verbatim, so the gate's and the narrowing's `authored` carry `subjects`, `source` and `implementations` too.
- Boundary: Windows and WSL. A WSL project's commands are parsed as POSIX and a native Windows project's as PowerShell.
- Callers of the lowering: `browseSource`, the pre-run live load in `lifecycle.ts`, `digest.ts`, `views.ts` and the CLI's `run --root` and `--workflows` call `loadWorkflowBundle`. The built-in generated workflows still call `loadBundle`: sync lowers its own permission set with `lowerPermissionSet`, and changeset-review and conformance declare none.
- Callers: app `startRun` compiles the run's policy with `compileRunPolicy` and the audit through `policyAuditRow`, calls `grantAlwaysGrantedTools` and `policyCanEscalate`, and hands the prompt executor `securityFloorOf`. The CLI does the same for every run it starts (`run`, `task start`, `task move`, `changeset review`, `workflow check`), through `governRun`, with the audit only where the run has a task; its approver is the terminal or a reasoned refusal. App `chatPlan` and `chatStartPlan` call `readPermissionSets`, word `effective.permissions` with `matchPermissionSet` in the bucket `bucketOf` answers, and hand both to the composer in `available`. App `savePermissionSet` checks a bucket, a name and a map and writes `permission-sets/<bucket>/<name>.json` through `writeFile`, which refuses the `system` layer. App `runChatMessage` reads the message's settings into one `Permission set` with `permissionSetOfSettings`, compiles a policy with no audit and that permission set folded into its baseline, calls `planAgentTools` and `gateTools`, and publishes the permission set on the turn's services with `withPermissionSetService` when the message declared tools. `chatOperationOf` writes the scope rules into a turn's `providerOptions`. `agentPromptRoutes` in [model-routing](model-routing.md) wraps every agent route in `withAgentPermissionSet` with that agent's declaration; `registerAgentRuntimes` registers the two claude functions with `wrapExecutor: agentFunctionWrapper(CLAUDE_TOOLS, …)` and wraps the codex function in `holdAgentFunction`, as `registerGenericAgents` wraps every generic CLI function. The CLI registers `run_command`, calls `policyCanEscalate`, and passes `executeWorkflow` the policy and approver `governRun` builds.

## Migration 16 dropped the audit's run column, and nothing else here is stored

- `command_log.run_id` was dropped by migration 16; it does not roll back. Every other input is configuration or snapshot data read at each start or turn, so a policy change applies to the next start or message without migration.
- The project `policy` block is moved once, at open, by `migrateSettingsLayers` in persistence `settingsMigration.ts` (2026-09-23; the steps are in [settings-json](../contracts/settings-json.md)). What it preserves and what it cannot:
  - A rule becomes one command line per permission set the layer can name — `program`, `subcommand` and `flags` as the words of the line (`git push --force`), `anyFlag` as one line per flag, `require_approval` as `ask` — written into the layer's own file, or as an override of a lower layer's that keeps following it. A set that offers no shell takes no line, and a withheld shell (`"bash": "deny"`) takes only denials, so the move never hands a set a shell.
  - A line the set already names keeps the set's mode. The old composition kept the stricter of rule and permission set, so a set whose line was looser than the rule is now looser; the report says which.
  - `argIncludes` cannot be said by a line: a deny or an ask is written for the whole command, which refuses or asks about more than the rule did; an allow is left out. A rule with no program, or a program-only rule whose program is a standard tool's name, is left out. All are reported.
  - First match won among rules; the most specific line wins among lines. A rule an earlier, broader one used to hide now decides its commands, and a rule that allowed a command the floor refuses (`git push` over `git push --force`) no longer reaches past the floor.
  - `policy.default` is carried onto each set's `bash` line where that line was looser — the old composition for a command nothing named — and `policy.toolDefault` onto a set with no `other`. A file utility on a line (`cat`, `rm`) answers to its file tool's line, which the default used to tighten too, and no longer does.
  - `policy.tools` is dropped: a set's own tool line already decided over it.
  - A line no permission set judges — `run_command`'s, a state's that declares no permission set, a map written inline on a state or sent by the composer — was judged by the rules and answers to the built-ins alone now. Where the shared root and a project both had rules, the project's used to replace the shared root's, and a set the project names from the shared root now holds both layers' lines.
  - A pinned snapshot is untouched; it never held the policy, which was read from the settings at each start.

## The one budget is the size above which a smart payload asks

- `askAboveBytes` defaults to 4194304, `DEFAULT_ASK_ABOVE_BYTES` in `packages/shared/src/config.ts`.

## Policy matches parsed intent, and an agent is held to its permission set where the route is known, both on purpose

- A verdict is decided over `ParsedCommand`s rather than a pattern over the raw line, so a flag in another position or a wrapper cannot change it; the cost is that a line the parser cannot model asks.
- A part is a request for a subject, never a member of a category. `git commit` and `rm` both write and deserve different answers, so there is no read, write or network class: a utility is the standard tool on its path, and everything else is its own name.
- The floor comes first, then the permission set. The permission set composes with the built-ins as the stricter of the two, so no permission set opens the floor. The one exception is an entry that names the program, which replaces a built-in ask or the default: those two stand in for a decision nobody had made, and naming the command is making it. `"bash": "allow"` names nothing, so it does not.
- There is no project rule list (2026-09-23). A command a project wants answered is a line under the `bash` tool of its permission sets, because a rule list beside the permission sets was a second place a command's answer lived, composed with the first by a rule — rules first, first match wins, a permission set may only tighten — that nobody reading one permission set could see. What stands above every permission set is the floor alone, and the project can turn it off (`functions.bash.builtins`) and do nothing else to it. The cost: a line no permission set judges — `run_command`'s, a state's that declares no permission set — answers to the built-ins alone, so what a project used to deny there with a rule now runs.
- The line's verdict is a narrowing, not only a `smart` verdict. Upstream hands a state's block to `scopeOf` and to nothing else, and a narrowing runs whatever mode the tool resolved to, so a remembered `bash: allow` cannot wave a later line's parts through. The cost is the decision kept in a `WeakMap` against the input object, which holds only while upstream passes that object through unchanged.
- The shell's entry is lowered as `ask` (it was upstream's `smart` until 2026-09-22). `deny` would refuse the `git status` the permission set allows, and `allow` would pre-approve a delegated agent's shell so that no line was judged; `ask` reaches the host with the line in hand every time, and the host's approver — `withPermissionFunctions` — lets through what the parts allow and puts the parts a function names to it. The cost is that the approver must be the wrapped one: a bare approver asks about every line.
- A function is a mode rather than a special word, because what decides a call per call is a program, and the person should be able to write it, configure it and have it ask them — which the approval prompt, being a function too, lets it do without being an approval itself. It is run through the engine as a one-state workflow so every callee kind the language has is one kind, and a callee that parks parks as a gate does. The one exception is a shell with no line left to judge: `deny` with nothing that allows, asks or defers a command is withheld, because a door only a conversation turn could see was shut stood open in a run and to codex.
- A run reads the state's block as a conversation turn does, because upstream hands it over whole. `literalPermissions` passes every key it does not read through verbatim, and the engine publishes the resolved block on `ExecServices.authored` beside the gate (declarative-ai 3f5e5cc). `subjects` merges per key of `permissions`, so a child's own replaces its parent's.
- `PERMISSION_SET_MARKERS` stay as the discriminator between a map and a state that declares no permission set, read off `ctx.authored`. An empty map and no declaration lower to the same block without them, and the two mean opposite things to an agent. They are still a pair, where one key would do, because every block lowered since the migration carries the pair, and a pinned snapshot's map would otherwise read as no declaration.
- A permission set is lowered before the engine rather than read by it. The engine owns reference expansion and `environment` merging and offers no hook between them, and it cannot be changed from this repository, so JaiRA resolves the one node it must rewrite with the engine's own exported resolver and hands over the shape the engine already takes. The cost is the inherited-`other` row above.
- A permission set inside a referenced block is lowered BESIDE the reference rather than by pasting the block in. Pasting would move every relative reference in the target (`./prompt.md`) to the state's file and change what it names; siblings of a `$ref` are the engine's own override, and its merge already makes a sibling `tools` list replace the target's map and sibling `permissions` win per key. The cost is that only `tools` and `permissions` are read off the target, by a small merge written to match the engine's.
- A CLI run is governed by the app's recipe, not a CLI one. `compileRunPolicy` and `securityFloorOf` are what `startRun` compiles, so a policy change reaches both hosts at once; what the CLI adds is only an approver. It has no answer that allows everything: a built-in ask is a question somebody should see, so the way past one unattended is to write the answer in the permission set that judged the line, or, where no permission set judges it, to turn the built-ins off, which the refusal names.
- An agent is held to its permission set by a wrapper around its executor rather than by the lowering or the chat wiring, because the native names are the agent's and which agent answers is not known until the route is. The removals travel on the two fields the upstream executor already reads to build `disallowedTools`, and a run's permission set is read back from `ctx.tools` and `ctx.authored`, so what an entry chose reaches the executor in a run as in a conversation turn. A claude agent reached as a function is held by the same wrapper, which upstream's function entry takes as `wrapExecutor`, because an ask rule is written into the op the entry builds and no wrapper of the function's `run` sees that op; codex and a generic CLI, whose holding reads the call's inputs, are held through `holdAgentFunction`.
- Codex is gated at its bridge rather than refused. It has no permission callback, but every call to one of our tools crosses the MCP bridge, and upstream puts it to the same gate claude's callback consults, with the same subject and input, before the tool runs. Codex is told to approve our tools on its side (`approval_mode = "approve"`), because a non-interactive `codex exec` has nobody to ask and cancels the call otherwise, and to treat the bridge as `required`, which makes it wait for the handshake instead of starting the turn without the tools. With ours served, the writing sandbox is how codex's own writers are displaced, so it opens only for a writer an entry keeps with `native`.
- A child that writes a permission set does not inherit its parent's implementation choices. A map is the whole statement of what a state holds and whose code serves it (decision 0007 §1); a child that wants its parent's permission set and more says so with `$ref` and siblings. Lowering writes `implementations` on every map so the engine's per-key merge replaces the parent's; `other` is still inherited where a child writes none, because a map cannot write "no `other`", and an unwritten one is the gate's last resort.
- The list form of `tools` and the old `permissions` modes are refused rather than read. They were read, with a list a grant rather than a fence, until every workflow had been migrated to a map (0007 step 7); after that the reader was code for a form nothing used, and a snapshot pinned before the migration is read as the new form, which is the row above.
- `gateTools` registers no profile table. What the tables existed for, an answer about a name nothing registered, is the permission set's `other` on the block the gate takes, and a map's `allow` now reaches the tool without asking.
