# Tool policy

## The unit decides what a tool call may do and where, and leaves remembering and asking to others

- `command.ts`: `takeApart(line, dialect)` turns a line into the requests it is made of, in the `posix` or `powershell` dialect ([0007](../decisions/0007-toolsets.md) §4): every command, every redirect, and every piece it could not model, each with its span in the original line. It comes apart at `&&`, `||`, `;`, `&`, `|`, newlines, `( … )`, `{ … }`, `$( … )`, backticks and `<( … )`; a here-document's body is data; `if`, `then`, `do` and `!` lead a command without being one. Embedders are opened recursively, with spans kept in the original line through a per-character offset map: `sh -c`, `powershell -Command`, `eval`, `exec`, `find -exec`, `xargs`, `env`, `sudo`, `nohup`, `time`, `timeout`, `nice`, `watch`, `parallel`, `ssh`, `docker exec`, `git -c alias.…`, `git submodule foreach`, `npx`, `pnpm dlx`. It skips the value a `-C` or `-c` flag takes, as in `git -C <dir>`. `parseCommand` is the same walk reported as `ParsedCommand`s. A line it cannot model comes back `unparsed` with a reason, an unreadable payload comes back as a request of kind `unparsed` beside the rest, and it never throws.
- `shellTables.ts`: the shell's tables, as data: `EMBEDDERS`, the utility → standard-tool tables `POSIX_UTILITIES` and `POWERSHELL_UTILITIES`, `NO_REQUEST`, `NULL_DEVICES`, `SCRIPT_INTERPRETERS`, `SCRIPT_RUNNERS` and `SCRIPT_EXTENSIONS`.
- `commandParts.ts` in runtime: `classifyRequest` names what a request is for: a standard tool on its paths or url, `script`, a command subject, or nothing. `shellToolsetOf` and `shellToolsetOfBlock` read a `Toolset` or a lowered block as the map a line is judged against, and `lookUp` answers for one part: the most specific command entry naming the program, then the part's own subject, then `other`, then `ask`.
- `commandParts.ts` in shared: the payload, `CommandApproval` and `CommandPart`, with `askingParts`, `entriesToRemember` and `chosenWidths`. `CommandApproval.toolset` names the toolset that judged the line: the reference a state names it by, or `inline`.
- `toolsetEdit.ts` in shared: "add to the toolset" as text in, text out. `addToToolsetText` sets entries in a toolset map, replacing a value where it stands, only the `mode` of an entry written as an object, and adding a new subject as one line after the last; `overrideToolsetText` writes a new file that starts from a lower layer's by an explicit root and refuses a bare `$`; `toolsetTextFollows` and `describeAddition` read one.
- `policy.ts`: `decideCommand(policy, line, dialect, options)` judges every part of a line and keeps the strictest verdict, returning the parts beside it. Per part: a `.jaira/` path denies; then authored `rules` with the first match winning, then the built-in denies for destructive git and `rm -r .git`, then the built-in asks for push, merge, network programs, publishing, installing, deploying and credential paths, then `default`; then the toolset's answer, the stricter of the two kept, except that an entry naming the program replaces a built-in ask or the default; a part the parser cannot vouch for asks at least; an answer remembered in `CommandGrants` settles a part that asks; and a scope table answers for the part's place by the standard tool the part is. `CommandGrants` keeps answers by width, never by line. `compilePolicy(policy, options)` turns `JairaPolicy` into upstream `ExecPolicy`, folding the per-tool modes of `options.toolset` over the project's in `baseline.tools`: `bash`, `run_command` and six other command tool names get `smart` in the baseline, `show_artifact` and every tool authored `smart` get a size-judging approver, a path under `.jaira/` is denied, and `scopeOf` narrows each call by the executor floor and the calling state's `permissions.scopes`, and for a command tool also by the line's own verdict: a deny always, an ask when a toolset is judging the line. The decision is kept against the call's input object, where the `smart` approver and `commandDecisionOf` find it again. `commandNarrowingOf` hands `gateTools` the line half alone. `policyCanEscalate` says whether a person could ever be asked.
- `approval.ts`: `ApprovalHub` parks an `ask` as an `ApprovalRequest`, which carries the decision's `parts` when the call was a shell line. `grants(taskId)` is the run's `CommandGrants`, emptied by `allow(taskId)`; `decide(requestId, decision, scope, remember)` stores the asking parts at the chosen widths and then answers upstream `once`.
- `tools.ts`: `gateTools` wraps named registry tools and builds a `ToolGate` over one `PermissionLedger` for one conversation turn; it reads modes from a `Toolset`, the one it is handed or the one it folds from `names` and the legacy `authored` block, writes the block the upstream gate takes from that map, and seeds no profile and registers no profile table. `grantAlwaysGrantedTools` adds `show_artifact` to every prompt state of a run's resolved bundle. `claudeReplacements` reads upstream's `replacesNative` map off the claude declaration. `scopeNarrowingFor` and `commandSubjects` build the per-call narrowing, and `partScopeFor` answers for one part of a line by the standard tool it is. `compileClaudeScopeRules` and `claudePermissionSettings` compile a scope table into Claude Code permission rules, one rule for every native of a standard tool. `createRunCommandFunction` builds `run_command`, which gates itself.
- `agentTools.ts` in runtime: what an agent is handed ([0007](../decisions/0007-toolsets.md) step 2). `CLAUDE_TOOLS`, `CODEX_TOOLS` and `GENERIC_CLI_TOOLS` are the executors' declarations, in the shape [agent-executors](agent-executors.md) describes. `planAgentTools(toolset, implementations, declaration)` resolves a toolset against one declaration into `inject`, `displaced`, `askNatives`, `denyNatives` and `switches`. Removing the built-in of a standard tool the toolset does not hold is what a toolset **map** does. A toolset marked `legacy`, the list form, keeps every built-in it does not mention and loses only what an explicit `deny` names, which includes the denies an old `read-only` profile reads as. `viewOfToolset` reads a toolset in hand and `viewOfServices` reads one back off the `ctx.tools` and `ctx.gate` the engine hands an executor, telling a lowered map from the legacy reading by asking the gate about the two `TOOLSET_MARKERS`. `withAgentToolset(declaration, executor, options)` hands a legacy run to the executor untouched, and otherwise applies the plan to one prompt call: for a `tools` transport it names the removed and displaced natives in a copy of `ctx.policy.baseline.tools` and answers `deny` for them from a copy of `ctx.gate`, which is where the upstream executor builds `disallowedTools` from, writes the kept natives into `providerOptions.claudeCode.settings.permissions.ask`, and asks the gate about a native by its standard name with `file_path` copied to the standard tool's path argument; for a `switches` transport it picks the executor for that setting of the switches; for `none` it refuses a toolset that denies anything. `agentServices` is the same removal for an agent reached as a function. `TOOLSET_SERVICE` and `withToolsetService` are how a caller that knows its toolset publishes it on the services bundle.
- `agentTools.ts` in shared: `AgentToolDeclaration` (`channel`, `natives`, `switches`) and the pure questions asked of one, `standardOfNative`, `nativesOfStandard`, `primaryNativeOf`, `unmappedNatives` and `replacementsOf`.
- `toolsets.ts` in shared: the toolset, the one map every reader of a grant and its modes consumes ([0007](../decisions/0007-toolsets.md) step 1). `Toolset` is `entries` (subject → `{kind, mode, implementation, offered}`) and `other`; it has no profile. `parseToolset` reads the authored map and reports a bad mode as an error and an unknown tool name as a warning. `resolveToolsetDecl` follows a bare-string reference and `$ref` with sibling overrides through an injected reader, and names a cycle. `toolsetOfLegacy` folds the old list and `permissions` block into the same shape and marks the result `legacy: true`, which nothing else sets: a listed tool takes `permissions.tools[name] ?? default`, a mode on an ungranted tool is kept un-offered, `default` becomes `other`, and an old `profile` of `read-only` or `plan` becomes the map it meant through `applyLegacyProfile`: every tool in the frozen `LEGACY_NON_READ_ONLY_TOOLS` (`edit`, `write_file`, `bash`) is `deny` and not offered whatever the list granted, and `other` is `deny`. `full`, and a custom name, change nothing. `offeredTools`, `toolModes`, `toolImplementations` and `shellSubjects` are what consumers read. `offeredTools` is what is handed to somebody, the list lowering writes and the set an agent plan calls held, so it leaves out a tool marked `unserved`; `holdsTool` and `heldTools` are what a person reads and counts, and count an unserved tool by its entry alone, because a lowered block read back has it un-offered. `declOfToolset` writes a toolset back out as the map an author would write: held lines only, an implementation only where it is `native`, a line with no mode as `ask`, and `other` always. `gateToolModes` is `toolModes` with the shell's entry as `smart`, which is how `bash` is lowered; its authored mode is carried in `subjects`, and `toolsetOfEnvironment` puts it back. `permissionsOfToolset` writes the two `TOOLSET_MARKERS` entries, `jaira:toolset+` as `allow` and `jaira:toolset-` as `deny`, into the `permissions.tools` of every toolset that is not legacy; `isLoweredToolset` reads them, and `toolsetOfEnvironment` strips them and drops the legacy mark when they are there. `lowerStateToolsets` rewrites a map-form state into the `tools` list and `permissions` block the upstream engine takes, in a state's `environment`, its `operation` and each child mount's `environment`, and returns a state with no toolset as the same object. `toolsetOfSettings` reads a message's `toolset`, which is what the composer writes, or the three fields a state's own declaration arrives as.
- `toolsetBuckets.ts` in shared: buckets, and which toolset a map is ([0007](../decisions/0007-toolsets.md) steps 4 and 5). `ToolsetChoice` is one toolset a card can offer: its id, bucket, name, layer and resolved map. `toolsetSignature` reduces a toolset to what it says: its held lines with mode and implementation, sorted, and `other`, with a tool the caller does not register left out. `sameToolset` and `matchToolset(current, choices, bucket, registered)` compare signatures, and a map that holds nothing matches nothing. `bucketOf` finds the bucket a conversation opens on by the same match, `chat` tried first and answered when nothing matches. `toolsetBuckets` lists the hierarchy with each bucket's layer and hint, `toolsetsOfBucket` orders a bucket's rows, and `toolsetLabel`, `toolsetHint`, `toolsetGlyph` and `toolsetSummary` word a row: the shipped files' words are a table in this file, and anybody else's toolset is its file name over a count of its lines. `toolsetNameProblem` and `toolsetBucketProblem` say what is wrong with a name a file or a folder cannot have.
- `builtin/toolsets/` in shared: the eight files that ship, `chat/{ask-first, read-only, auto, full}.json` and `chat_control/` with the same four names. The `chat` four hold every tool a conversation can be handed, with the modes the composer's four presets wrote, and end in the `other` that preset gave a name it had never heard of: `ask`, `deny`, `smart`, `allow`. The `chat_control` four hold only `workflows`, `start`, `move`, `tasks`, `answer`, `hold`, `release` and `stop`, with `other: "deny"`; its `read-only` allows `workflows` and `tasks` and denies the rest.
- `toolsets.ts` in persistence: `loadWorkflowBundle` is `loadBundle` behind that lowering, used by the browser, the pre-run load, the digest, the state views and the CLI. `toolsetReader` resolves a toolset reference with upstream `resolveReference` and the bundle's own options, so `$/toolsets/<bucket>/<name>` searches `paths.roots` in order and the file reaches `onReferencedFile`. `listToolsets(roots)` lists `toolsets/<bucket>/<name>.json` across the layer roots, first root winning, buckets free to nest. `readToolsets(paths)` reads each of them through `toolsetReader` into a `ToolsetChoice` with its layer and its map with references followed, and leaves out a file that does not resolve or does not parse.
- `toolVocabulary.ts`: `TOOL_SPECS`, the one table of standard tool names with category, `pathArgs`, `urlArgs`, `nativeOnly`, `alwaysGranted` and `unserved`. It holds no agent's native names, no `readOnly` and no profile. The category `tasks`, drawn as Tasks & workflows, holds the eight workflow tools of [0005](../decisions/0005-connect.md) §3, each marked `unserved: true`: the name is known, so a toolset may hold it and the linter does not warn, and nothing registers an implementation. `offeredTools`, `planAgentTools` and `JAIRA_TOOLS` each skip an unserved tool, and `isServedTool` answers for one name.
- `toolsetEdit.ts` in shared and `addToToolset` / `toolsetWriteTargets` in persistence `toolsets.ts`: "Add to the toolset" ([0007](../decisions/0007-toolsets.md) step 3). A layer that holds the file gets the line added in place, byte for byte elsewhere; a layer that does not gets an override `{ "$ref": "$SYSTEM|$BASE/toolsets/…", "<subject>": "<mode>" }` that keeps following the lower layer. Only a bare `$/toolsets/<bucket>/<name>` reference is writable; lowering records which toolset a block came from as `permissions.source` (the reference, or `inline`), and the policy puts it on `CommandApproval.toolset`.
- `agentHanded.ts` in runtime and `toolsetMigration.ts` in persistence: migrating the authored workflows ([0007](../decisions/0007-toolsets.md) step 7). `handedToClaude(environment)` MEASURES what a delegated claude is handed under one effective block, by running a one-state workflow through the engine, `withAgentToolset` and the upstream executor to the query options a real `claude` would be spawned with (a fake `AgentQuery` stands in for the binary alone): what is served, removed and pre-approved, and — by asking the spawn's own `canUseTool` — what decides a call by every name the agent can still address, the shell by one line per kind of part (`SHELL_PROBES`). `handedDifferences` compares two by reach and decision rather than by which implementation serves a tool; a way in that is refused is not a way in, a shell every line of which is refused is not a shell, and a native removed up front and one refused at the callback are one answer. `planToolsetMigration` walks the `children` tree with upstream's `mergeOperationFields` to get each block's EFFECTIVE grant, writes the map that measures the same — a toolset on the search path, one plus a few lines, or an inline map, `other` always written — and then measures every state under every chain at every level before and after, taking a file back out and measuring again if any state fails under it. `applyToolsetMigration` writes, refusing the shared root without `sharedRoot` and copying `workflows/` to a timestamped backup first. `toolsetMigrateEdit.ts` in shared is the text half: `rewriteToolsBlocksText` (jsonc-parser to locate, hand-spliced to write; the `yaml` Document for YAML), `rewriteToolsBlocksValue` as what the text must parse to, and `unifiedDiff`.
- `scopes.ts`: glob matching and `resolveScope`, `resolveUrlScope`, `resolveScopes`, `scopeModeOf` and `layeredScopeMode`. The most specific glob that says anything about the tool decides, an unmatched place is denied, and a call about several places takes the strictest answer.
- `operationVocabulary.ts`: `PERMISSION_MODES`, `PermissionsDecl` with the `subjects` and `implementations` keys lowering writes and a `profile` that is read and never written, `ChatSettings` with its optional `toolset`, `ToolImplementation`, `ToolChoice` with the native name each agent route has for the tool, and `ChatPlanView.available` with the `toolsets` and the `bucket` the composer's Permissions card draws. The function presets are gone; `READ_ONLY_PRESET_TOOLS` is kept frozen for the tests that hold `chat/read-only` to the map the preset wrote. The same file holds the operation field tables the authoring form and the operation schema read.
- `commandLog.ts`: `CommandLog.record`, `list` and `summary` over `command_log`. In `service.ts`, `startRun` passes `compilePolicy` an `onDecision` that writes one row per decision, and `scopeFloorOf` reads the floor.

It deliberately does not own:

- Resolving a mode through the ledger, and escalating: upstream `decideToolCall`, `PermissionLedger`, `withPermission` and `createToolGate` in `@declarative-ai/permissions`. Upstream still has profiles: a state file left in the list form reaches the engine as written, so a `permissions.profile` in it is still seeded there, and upstream's own `read-only` handling composes with the plan above.
- Building `disallowedTools`, `allowedTools` and the permission callback from the services an executor is handed: upstream `AgentExecutor` in `@declarative-ai/agents-api`.
- Parking an approval for a person and attaching the policy's reason: [interaction-hub](interaction-hub.md). The inbox channels: [inbox-channels](../contracts/inbox-channels.md).
- Expanding every other reference in a state, merging `environment` layers, and resolving a lowered `tools` list against the registry: upstream `@declarative-ai/hw`. It reads a non-array `tools` as a binding and refuses a map with `unrecognized binding form`, which is why lowering happens before it.
- The tools themselves: [host-tools](host-tools.md) and [host-tool-vocabulary](../contracts/host-tool-vocabulary.md).
- Parsing `policy` and executor `scopes`: [project-config](project-config.md), with the shapes in [settings-json](../contracts/settings-json.md). Folding the compiled floor over every prompt call: `withSecurityFloor` in [executor-tree](executor-tree.md).
- Deleting `command_log` rows: [history-pruning](history-pruning.md) and [task-lifecycle](task-lifecycle.md).

## The unit is core logic behind the upstream permission seams, compiled once per run and once per turn

- Layer `core`. The runtime and shared files import upstream packages, `@jaira/shared` and `paths.ts` from [process-exec](process-exec.md), whose `dialectFor` picks the parser dialect by the same rule `interpreterFor` picks the shell, so the language judged is the language run. `commandLog.ts` is persistence code and the wiring is main-process code.
- Upstream seams: `ExecPolicy` with `baseline`, `smart` and `scopeOf`, and `Approver`, reach the engine on the services seam as `ctx.policy` and `ctx.approve`. `ScopeNarrowing` is the `scopeOf` callback. `ToolGate` is what a delegated agent's permission callback consults. `providerOptions.claudeCode.settings.permissions` carries `allow`, `ask` and `deny` rules to Claude Code. `ExecServices.tools`, `ExecServices.gate` and `ExecServices.policy` are what `withAgentToolset` reads a run's toolset back from and what it hands the agent executor copies of.
- Boundary: Windows and WSL. A WSL project's commands are parsed as POSIX and a native Windows project's as PowerShell.
- Callers of the lowering: `browseSource`, the pre-run live load in `lifecycle.ts`, `digest.ts`, `views.ts` and the CLI's `run --root` and `--workflows` call `loadWorkflowBundle`. The built-in sync, changeset-review and conformance workflows are generated in the list form and still call `loadBundle`.
- Callers: app `startRun` compiles the run's policy with the floor, `workspaceRoot`, `askAboveBytes` and the audit, calls `grantAlwaysGrantedTools` and `policyCanEscalate`, and compiles the floor into Claude rules for the prompt executor. App `chatPlan` and `chatStartPlan` call `readToolsets`, word `effective.permissions` with `matchToolset` in the bucket `bucketOf` answers, and hand both to the composer in `available`. App `saveToolset` checks a bucket, a name and a map and writes `toolsets/<bucket>/<name>.json` through `writeFile`, which refuses the `system` layer. App `runChatMessage` reads the message's settings into one `Toolset` with `toolsetOfSettings`, compiles a policy with no audit and that toolset folded into its baseline, calls `planAgentTools` and `gateTools`, and publishes the toolset on the turn's services with `withToolsetService` when the message declared tools. `chatOperationOf` writes the scope rules into a turn's `providerOptions`. `agentPromptRoutes` in [model-routing](model-routing.md) wraps every agent route in `withAgentToolset` with that agent's declaration, and `registerAgentRuntimes` wraps the two claude functions in `agentServices`. The CLI registers `run_command` and calls `policyCanEscalate`, and passes no policy to `executeWorkflow`.

## The invariants keep a risky call from resolving to allow and a narrowing from widening

| # | Invariant | Asserted by |
| --- | --- | --- |
| 1 | A destructive command never resolves to allow, however it is spelled, whatever shares its line and whatever the toolset allows | `policy.test.ts` "denies the same operations however they are dressed up", "takes the strictest verdict on a line", "keeps the destructive floor and `.jaira/` above EVERY toolset, however the command is dressed"; `command.test.ts` "finds a destructive command hidden after a benign one", "strips prefix wrappers (env, sudo, npx)"; `toolsetPolicy.test.ts` "JUDGES a shell line against the toolset's command subjects — and keeps the floor above them" |
| 2 | A line the parser cannot model is never allowed without asking, and a deny beside the unreadable piece stands | `policy.test.ts` "asks rather than allows: %j", "a line the parser cannot model asks, whatever the toolset allows — and a deny beside it stands"; `command.test.ts` "reports an unterminated quote", "refuses to model PowerShell expression syntax", "reports an unreadable PAYLOAD as a piece, beside everything it could read"; `scopeWalkAndCommand.test.ts` "escalates a line it could not parse" |
| 3 | A path under `.jaira/` is denied to command and file tools at any size | `policy.test.ts` "denies .jaira wherever it appears", "denies .jaira/ by path, for command and file tools alike", "still refuses .jaira/ whatever the size", "keeps the destructive floor and `.jaira/` above EVERY toolset, however the command is dressed" |
| 4 | A matching authored rule is never overridden by a built-in, and a toolset may tighten it and never loosen it | `policy.test.ts` "takes precedence over the built-ins, first match winning", "honours a custom default and lets built-ins be disabled", "composes with the command policy: rules and the floor first, then the toolset" |

## Policy matches parsed intent, and an agent is held to its toolset where the route is known, both on purpose

- A verdict is decided over `ParsedCommand`s rather than a pattern over the raw line, so a flag in another position or a wrapper cannot change it; the cost is that a line the parser cannot model asks.
- A part is a request for a subject, never a member of a category. `git commit` and `rm` both write and deserve different answers, so there is no read, write or network class: a utility is the standard tool on its path, and everything else is its own name.
- Rules and the floor come first, then the toolset. The toolset composes as the stricter of the two, so a state can tighten the project's policy and cannot widen it. The one exception is an entry that names the program, which replaces a built-in ask or the default: those two stand in for a decision nobody had made, and naming the command is making it. `"bash": "allow"` names nothing, so it does not.
- The line's verdict is a narrowing, not only a `smart` verdict. Upstream hands a state's block to `scopeOf` and to nothing else, and a narrowing runs whatever mode the tool resolved to, so a remembered `bash: allow` cannot wave a later line's parts through. The cost is the decision kept in a `WeakMap` against the input object, which holds only while upstream passes that object through unchanged.
- The shell's entry is lowered as `smart`. Any other mode would let upstream answer for the tool before the line was read: `deny` would refuse the `git status` the toolset allows, and `allow` would pre-approve a delegated agent's shell so that no line was judged.
- A toolset is lowered before the engine rather than read by it. The engine owns reference expansion and `environment` merging and offers no hook between them, and it cannot be changed from this repository, so JaiRA resolves the one node it must rewrite with the engine's own exported resolver and hands over the shape the engine already takes. The cost is the inherited-`other` row above.
- An agent is held to its toolset by a wrapper around its executor rather than by the lowering or the chat wiring, because the native names are the agent's and which agent answers is not known until the route is. The removals travel on the two fields the upstream executor already reads to build `disallowedTools`, so no upstream change was needed; the cost is that a run's toolset is read back from `ctx.tools` and `ctx.gate`, which cannot say whose implementation an entry chose.
- The list form is the legacy reading and is not held to the map's rule. The workflows people run are lists that lean on the agent's own search and web tools, step 1 promised that an unmigrated state runs exactly as before, and whether a state means "these and nothing else" is a choice its author makes when it is migrated (0007 step 7), not one to infer. A run sees only a gate, so a lowered map says it was a map with two entries of different modes that no tool is named by: a gate answers `other` for a name it has no entry for, and two answers that disagree can only be entries.
- `gateTools` registers no profile table. What the tables existed for, an answer about a name nothing registered, is the toolset's `other` on the block the gate takes, and a map's `allow` now reaches the tool without asking.
