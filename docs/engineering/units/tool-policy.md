# Tool policy

## The unit decides what a tool call may do and where, and leaves remembering and asking to others

- `command.ts`: `parseCommand(line, dialect)` turns a line into `ParsedCommand`s in the `posix` or `powershell` dialect. It splits on separators, unwraps shell wrappers such as `sh -c` and `powershell -Command`, unwraps prefix wrappers such as `env`, `sudo`, `npx` and `pnpm`, and skips the value a `-C` or `-c` flag takes, as in `git -C <dir>`. A line it cannot model comes back `unparsed` with a reason, and it never throws.
- `policy.ts`: `decideCommand(policy, line, dialect)` judges every command on a line, authored `rules` first with the first match winning, then the built-in denies for destructive git and `rm -r .git`, then the built-in asks for push, merge, network programs, publishing, installing, deploying and credential paths, and keeps the strictest verdict. `compilePolicy(policy, options)` turns `JairaPolicy` into upstream `ExecPolicy`, folding the per-tool modes of `options.toolset` over the project's in `baseline.tools`: `bash`, `run_command` and six other command tool names get `smart` in the baseline, `show_artifact` and every tool authored `smart` get a size-judging approver, a path under `.jaira/` is denied, and `scopeOf` narrows each call by the executor floor and the calling state's `permissions.scopes`. `policyCanEscalate` says whether a person could ever be asked.
- `tools.ts`: `gateTools` wraps named registry tools and builds a `ToolGate` over one `PermissionLedger` for one conversation turn; it reads modes from a `Toolset`, the one it is handed or the one it folds from `names` and the legacy `authored` block, writes the block the upstream gate takes from that map, and seeds no profile and registers no profile table. `grantAlwaysGrantedTools` adds `show_artifact` to every prompt state of a run's resolved bundle. `claudeReplacements` reads upstream's `replacesNative` map off the claude declaration. `scopeNarrowingFor` and `commandSubjects` build the per-call narrowing. `compileClaudeScopeRules` and `claudePermissionSettings` compile a scope table into Claude Code permission rules, one rule for every native of a standard tool. `createRunCommandFunction` builds `run_command`, which gates itself.
- `agentTools.ts` in runtime: what an agent is handed ([0007](../decisions/0007-toolsets.md) step 2). `CLAUDE_TOOLS`, `CODEX_TOOLS` and `GENERIC_CLI_TOOLS` are the executors' declarations, in the shape [agent-executors](agent-executors.md) describes. `planAgentTools(toolset, implementations, declaration)` resolves a toolset against one declaration into `inject`, `displaced`, `askNatives`, `denyNatives` and `switches`. Removing the built-in of a standard tool the toolset does not hold is what a toolset **map** does. A toolset marked `legacy`, the list form, keeps every built-in it does not mention and loses only what an explicit `deny` names, which includes the denies an old `read-only` profile reads as. `viewOfToolset` reads a toolset in hand and `viewOfServices` reads one back off the `ctx.tools` and `ctx.gate` the engine hands an executor, telling a lowered map from the legacy reading by asking the gate about the two `TOOLSET_MARKERS`. `withAgentToolset(declaration, executor, options)` hands a legacy run to the executor untouched, and otherwise applies the plan to one prompt call: for a `tools` transport it names the removed and displaced natives in a copy of `ctx.policy.baseline.tools` and answers `deny` for them from a copy of `ctx.gate`, which is where the upstream executor builds `disallowedTools` from, writes the kept natives into `providerOptions.claudeCode.settings.permissions.ask`, and asks the gate about a native by its standard name with `file_path` copied to the standard tool's path argument; for a `switches` transport it picks the executor for that setting of the switches; for `none` it refuses a toolset that denies anything. `agentServices` is the same removal for an agent reached as a function. `TOOLSET_SERVICE` and `withToolsetService` are how a caller that knows its toolset publishes it on the services bundle.
- `agentTools.ts` in shared: `AgentToolDeclaration` (`channel`, `natives`, `switches`) and the pure questions asked of one, `standardOfNative`, `nativesOfStandard`, `primaryNativeOf`, `unmappedNatives` and `replacementsOf`.
- `toolsets.ts` in shared: the toolset, the one map every reader of a grant and its modes consumes ([0007](../decisions/0007-toolsets.md) step 1). `Toolset` is `entries` (subject → `{kind, mode, implementation, offered}`) and `other`; it has no profile. `parseToolset` reads the authored map and reports a bad mode as an error and an unknown tool name as a warning. `resolveToolsetDecl` follows a bare-string reference and `$ref` with sibling overrides through an injected reader, and names a cycle. `toolsetOfLegacy` folds the old list and `permissions` block into the same shape and marks the result `legacy: true`, which nothing else sets: a listed tool takes `permissions.tools[name] ?? default`, a mode on an ungranted tool is kept un-offered, `default` becomes `other`, and an old `profile` of `read-only` or `plan` becomes the map it meant through `applyLegacyProfile`: every tool in the frozen `LEGACY_NON_READ_ONLY_TOOLS` (`edit`, `write_file`, `bash`) is `deny` and not offered whatever the list granted, and `other` is `deny`. `full`, and a custom name, change nothing. `offeredTools`, `toolModes`, `toolImplementations` and `shellSubjects` are what consumers read. `permissionsOfToolset` writes the two `TOOLSET_MARKERS` entries, `jaira:toolset+` as `allow` and `jaira:toolset-` as `deny`, into the `permissions.tools` of every toolset that is not legacy; `isLoweredToolset` reads them, and `toolsetOfEnvironment` strips them and drops the legacy mark when they are there. `lowerStateToolsets` rewrites a map-form state into the `tools` list and `permissions` block the upstream engine takes, in a state's `environment`, its `operation` and each child mount's `environment`, and returns a state with no toolset as the same object. `toolsetOfSettings` reads a message's `toolset`, or the three fields the composer still writes.
- `toolsets.ts` in persistence: `loadWorkflowBundle` is `loadBundle` behind that lowering, used by the browser, the pre-run load, the digest, the state views and the CLI. `toolsetReader` resolves a toolset reference with upstream `resolveReference` and the bundle's own options, so `$/toolsets/<bucket>/<name>` searches `paths.roots` in order and the file reaches `onReferencedFile`. `listToolsets(roots)` lists `toolsets/<bucket>/<name>.json` across the layer roots, first root winning, buckets free to nest.
- `toolVocabulary.ts`: `TOOL_SPECS`, the one table of standard tool names with category, `pathArgs`, `urlArgs`, `nativeOnly` and `alwaysGranted`. It holds no agent's native names, no `readOnly` and no profile.
- `scopes.ts`: glob matching and `resolveScope`, `resolveUrlScope`, `resolveScopes`, `scopeModeOf` and `layeredScopeMode`. The most specific glob that says anything about the tool decides, an unmatched place is denied, and a call about several places takes the strictest answer.
- `operationVocabulary.ts`: `PERMISSION_MODES`, `PermissionsDecl` with the `subjects` and `implementations` keys lowering writes and a `profile` that is read and never written, `ChatSettings` with its optional `toolset`, `ToolImplementation`, `ToolChoice` with the native name each agent route has for the tool, and the composer's `PERMISSION_PRESETS` with `presetModes` and `presetOf`. The `read-only` preset allows the tools named in `READ_ONLY_PRESET_TOOLS` and denies every other name. The same file holds the operation field tables the authoring form and the operation schema read.
- `commandLog.ts`: `CommandLog.record`, `list` and `summary` over `command_log`. In `service.ts`, `startRun` passes `compilePolicy` an `onDecision` that writes one row per decision, and `scopeFloorOf` reads the floor.

It deliberately does not own:

- Resolving a mode through the ledger, and escalating: upstream `decideToolCall`, `PermissionLedger`, `withPermission` and `createToolGate` in `@declarative-ai/permissions`. Upstream still has profiles: a state file left in the list form reaches the engine as written, so a `permissions.profile` in it is still seeded there, and upstream's own `read-only` handling composes with the plan above.
- Building `disallowedTools`, `allowedTools` and the permission callback from the services an executor is handed: upstream `AgentExecutor` in `@declarative-ai/agents-api`.
- Parking an approval for a person and attaching the policy's reason: [interaction-hub](interaction-hub.md). The inbox channels: [inbox-channels](../contracts/inbox-channels.md).
- Expanding every other reference in a state, merging `environment` layers, and resolving a lowered `tools` list against the registry: upstream `@declarative-ai/hw`. It reads a non-array `tools` as a binding and refuses a map with `unrecognized binding form`, which is why lowering happens before it.
- The tools themselves: [host-tools](host-tools.md) and [host-tool-vocabulary](../contracts/host-tool-vocabulary.md).
- Parsing `policy` and executor `scopes`: [project-config](project-config.md), with the shapes in [settings-json](../contracts/settings-json.md). Folding the compiled floor over every prompt call: `withSecurityFloor` in [executor-tree](executor-tree.md).
- Deleting `command_log` rows: [history-pruning](history-pruning.md) and [task-lifecycle](task-lifecycle.md).

## The unit is core logic behind the upstream permission seams, compiled once per run and once per turn

- Layer `core`. The runtime and shared files import upstream packages, `@jaira/shared` and `paths.ts` from [process-exec](process-exec.md), whose `dialectFor` picks the parser dialect by the same rule `interpreterFor` picks the shell, so the language judged is the language run. `commandLog.ts` is persistence code and the wiring is main-process code.
- Upstream seams: `ExecPolicy` with `baseline`, `smart` and `scopeOf`, and `Approver`, reach the engine on the services seam as `ctx.policy` and `ctx.approve`. `ScopeNarrowing` is the `scopeOf` callback. `ToolGate` is what a delegated agent's permission callback consults. `providerOptions.claudeCode.settings.permissions` carries `allow`, `ask` and `deny` rules to Claude Code. `ExecServices.tools`, `ExecServices.gate` and `ExecServices.policy` are what `withAgentToolset` reads a run's toolset back from and what it hands the agent executor copies of.
- Boundary: Windows and WSL. A WSL project's commands are parsed as POSIX and a native Windows project's as PowerShell.
- Callers of the lowering: `browseSource`, the pre-run live load in `lifecycle.ts`, `digest.ts`, `views.ts` and the CLI's `run --root` and `--workflows` call `loadWorkflowBundle`. The built-in sync, changeset-review and conformance workflows are generated in the list form and still call `loadBundle`.
- Callers: app `startRun` compiles the run's policy with the floor, `workspaceRoot`, `askAboveBytes` and the audit, calls `grantAlwaysGrantedTools` and `policyCanEscalate`, and compiles the floor into Claude rules for the prompt executor. App `runChatMessage` reads the message's settings into one `Toolset` with `toolsetOfSettings`, compiles a policy with no audit and that toolset folded into its baseline, calls `planAgentTools` and `gateTools`, and publishes the toolset on the turn's services with `withToolsetService` when the message declared tools. `chatOperationOf` writes the scope rules into a turn's `providerOptions`. `agentPromptRoutes` in [model-routing](model-routing.md) wraps every agent route in `withAgentToolset` with that agent's declaration, and `registerAgentRuntimes` wraps the two claude functions in `agentServices`. The CLI registers `run_command` and calls `policyCanEscalate`, and passes no policy to `executeWorkflow`.

## The settings and the snapshot hold the rules, and the database holds only the audit

| Data | Read / written | Source of truth | Who else touches it |
| --- | --- | --- | --- |
| `policy` | read unchecked by `compilePolicy` and `policyCanEscalate` | layered `settings.json` | project-config requires only that it is an object |
| `artifacts.askAboveBytes` | read into `compilePolicy` | layered `settings.json` | artifact-placement reads the rest of `artifacts` |
| Root `scopes` of the first executor that has any | read by `scopeFloorOf` | layered `settings.json` | executor-tree parses the executor nodes |
| A state's or a message's `permissions` | read at each decision | the pinned snapshot, or the composer's overrides | chat-turns folds the overrides |
| A state's toolset, `environment.tools` as a map or a reference | lowered at every load into `tools` and `permissions`, with command subjects under `permissions.subjects` and implementations under `permissions.implementations` | the state file and the `toolsets/<bucket>/<name>.json` it names, across `paths.roots`; after a start, the pinned snapshot, which stores the lowered state | upstream merges the lowered fields down the `environment` chain |
| `command_log` rows | written by the run's `onDecision` through `CommandLog.record`; read by `list` and `summary` | the project database, under every storage mode | board-projection draws them; history-pruning and task-lifecycle delete them |
| `PermissionLedger` | built by each `gateTools` call and each `run_command` command | memory | upstream decides against it |

## A conversation turn and a CLI run are governed far less than an app run, and the audit records only policy's side

| When | Behavior | Recovery | UX state |
| --- | --- | --- | --- |
| A line does not parse, or holds PowerShell `$(`, `@(`, a backtick or `iex` | `require_approval` with `command could not be parsed (<reason>)` | the person decides | an approval for the raw line |
| An agent runs `pnpm publish` or `pnpm add <pkg>` | `pnpm` is a prefix wrapper, so the program reads as `publish` or `add`, the publish and install asks never match, and the verdict is allow | author a rule whose `program` is the word after `pnpm` | the command runs without asking |
| A person answers an approval with `session`, `workflow-run` or `always` | the answer lives in the ledger that asked; `gateTools` builds one per turn and `run_command` one per command | none | the next turn or command asks again |
| A conversation turn's tool call names a place the executor floor refuses | `gateTools` is given no floor and does not read `policy.scopeOf`, and the chat executor gets no compiled floor, so the gate and the wrapped tools narrow only by the message's own `permissions.scopes` | none | the call asks as if no floor existed |
| A state is still written as a list, with or without the old `permissions` block, or declares no tools | it is the legacy reading and runs exactly as it did: a run is handed to the agent executor untouched, so claude keeps the built-in of every tool the list does not mention, `Glob`, `Grep`, `WebFetch` and `WebSearch` among them, and only the engine's own handling of a `profile` removes anything. The composer still writes the list form, so a conversation turn is legacy too: its plan removes what an explicit `deny` names and what an injected tool displaces | migrate the state to a map, which is where it chooses ([0007](../decisions/0007-toolsets.md) step 7) | a list-form workflow behaves as it did before toolsets |
| A toolset map leaves out a standard tool | the agent's built-in for it is removed: a map holding only `read_file` does not have claude's `Glob`, `Grep`, `WebFetch` or `WebSearch` | hold `glob`, `grep` or the web tools; JaiRA serves all four | the agent has the held tools and `show_artifact`, and nothing else |

## Migration 16 dropped the audit's run column, and nothing else here is stored

- `command_log.run_id` was dropped by migration 16; it does not roll back. Every other input is configuration or snapshot data read at each start or turn, so a policy change applies to the next start or message without migration.

## The one budget is the size above which a smart payload asks

- `askAboveBytes` defaults to 4194304, `DEFAULT_ASK_ABOVE_BYTES` in `packages/shared/src/config.ts`.

## Policy matches parsed intent, and an agent is held to its toolset where the route is known, both on purpose

- A verdict is decided over `ParsedCommand`s rather than a pattern over the raw line, so a flag in another position or a wrapper cannot change it; the cost is that a line the parser cannot model asks.
- A toolset is lowered before the engine rather than read by it. The engine owns reference expansion and `environment` merging and offers no hook between them, and it cannot be changed from this repository, so JaiRA resolves the one node it must rewrite with the engine's own exported resolver and hands over the shape the engine already takes. The cost is the inherited-`other` row above.
- An agent is held to its toolset by a wrapper around its executor rather than by the lowering or the chat wiring, because the native names are the agent's and which agent answers is not known until the route is. The removals travel on the two fields the upstream executor already reads to build `disallowedTools`, so no upstream change was needed; the cost is that a run's toolset is read back from `ctx.tools` and `ctx.gate`, which cannot say whose implementation an entry chose.
- The list form is the legacy reading and is not held to the map's rule. The workflows people run are lists that lean on the agent's own search and web tools, step 1 promised that an unmigrated state runs exactly as before, and whether a state means "these and nothing else" is a choice its author makes when it is migrated (0007 step 7), not one to infer. A run sees only a gate, so a lowered map says it was a map with two entries of different modes that no tool is named by: a gate answers `other` for a name it has no entry for, and two answers that disagree can only be entries.
- `gateTools` registers no profile table. What the tables existed for, an answer about a name nothing registered, is the toolset's `other` on the block the gate takes, and a map's `allow` now reaches the tool without asking.
