# Tool policy

## The unit decides what a tool call may do and where, and leaves remembering and asking to others

- `shellCommand.ts` (in `@jaira/shared`, so the conversation can draw a line the way an approval does): `takeApart(line, dialect)` turns a line into the requests it is made of, in the `posix`, `powershell` or `cmd` dialect ([0007](../decisions/0007-permissionSets.md) §4): every command, every redirect, every piece of code nobody can read off the line (`code`, the subject `script`), every piece it read and nobody can vouch for (`unvouched`, which asks and says why), and every piece it could not model (`unparsed`, which says it could not be parsed), each with its span in the original line; a command request carries the dialect it was written in, which is a payload's own inside a line of another (`powershell -Command "…"` in a POSIX line). A PowerShell text is `powershellCommand.ts`'s; `cmd /c`'s payload is cmd's, where `&` is a separator, `^` escapes, `'` is a character, `%VAR%` is decided at run time, `@` before a command is dropped and `if`, `for` and `goto` are not modelled. `commandNameOf` reads a command word in a dialect — in PowerShell an alias is the cmdlet it runs (`rm` → `remove-item`, kept as `alias`) unless the word names a path or an extension (`where.exe`) — and `powershellParameter` reads a PowerShell parameter in any case, after any of its dashes, cut short to a prefix that names one of a list alone. `nativeShellDialect(tool)` is the language an agent's own shell tool runs its line in: Claude Code's `Bash` POSIX (Git Bash on Windows too), its `PowerShell` PowerShell, and any other shell tool the project's (`dialectFor`). In POSIX a line comes apart at `&&`, `||`, `;`, `&`, `|`, newlines, `( … )`, `{ … }`, `$( … )`, backticks and `<( … )`; a here-document's body is data; `if`, `then`, `do` and `!` lead a command without being one. Embedders are opened recursively, with spans kept in the original line through a per-character offset map: `sh -c`, `powershell -Command`, `eval`, `exec`, `find -exec`, `xargs`, `env`, `sudo`, `nohup`, `time`, `timeout`, `nice`, `watch`, `parallel`, `ssh`, `docker exec`, `git -c alias.…`, `git submodule foreach`, `npx`, `pnpm dlx`. It skips the value a `-C` or `-c` flag takes, as in `git -C <dir>`, and keeps the flags written before the subcommand apart as `leadingFlags` — the program's own options, as against the subcommand's. A command runner it opens (`COMMAND_RUNNERS`: `sh -c`, `env`, `sudo`, `npx`, …) comes back first as a request of its own marked `opened` — `kept` for an embedder that was one already (`ssh`, `docker exec`) — which the runner gate judges and which `commands` leaves out when it was not kept. A command's leading `VAR=value` words, and those of an embedder it was opened from (`env FOO=1 git diff`), are kept on it by name as `sets`; a segment of nothing but assignments sets a variable for the rest of the line, and comes back as an `unvouched` request unless every name is harmless or shell-local. `parseCommand` is the same walk reported as `ParsedCommand`s. A line it cannot model comes back `unparsed` with a reason, an unreadable payload comes back as a request of kind `unparsed` beside the rest, and it never throws.
- `powershellCommand.ts` (in `@jaira/shared`, internal to `shellCommand.ts`, with `shellWords.ts` holding the token and walk shapes the two hand each other): `walkPowerShell` reads a PowerShell text as PowerShell's own parser does — calibrated against `[System.Management.Automation.Language.Parser]`. A statement is a command, an expression, an assignment or a keyword's: `if`/`elseif`/`else`, `foreach`, `for`, `while`, `do … while|until`, `switch` (its clauses are values; `-File` is a read of the file), `try`/`catch`/`finally`, `trap`, `param`, `begin`/`process`/`end`, `return`/`throw`/`exit`, `break`/`continue`, `using`, `data`; a keyword's block ends its statement, and `;`, newlines, `|`, PowerShell 7's `&&`, `||` and background `&` separate the rest. A command — by name, or after the call operator `&` or dot-source `.` — has words, parameters (`-Path x`; `-Path:x`, whose value is `bound`; any dash; a name ending at `.`), arrays (`a, b`, each word after the first an `element`), redirects (`>`, `>>`, `2>`, `*>`; `2>&1` joins streams and names no place; `<` is refused, as PowerShell refuses it) and `--%`, after which the rest of the line is words as written. Code runs, and is taken apart where it is written, in `$( … )`, `@( … )`, `( … )`, a script block `{ … }` (handed on as a `code` word), a hash literal's values, an expandable string's and a here-string's `$( … )`; a single-quoted string and a literal here-string run nothing; a word that starts with a quote ends with it, `(` and `{` end a word, `>` inside one is a character of it, and a backtick escapes. A .NET call (`[IO.File]::WriteAllText(…)`, `(Get-Item x).Delete()`), a property set on an object and a variable on a drive that is no scope's (`${C:\x}`, `$HKCU:Software`) are `code` unless the call is in `POWERSHELL_PURE_METHODS` or `POWERSHELL_PURE_STATICS`; an assignment to `$env:X` (unless harmless), `$function:x`, `$alias:x` or `$PSDefaultParameterValues` is an `unvouched` piece, as is `using module`/`assembly`; `function`, `filter`, `workflow`, `configuration`, `class` and `enum` are not modelled and leave the line unparsed, their bodies judged all the same. A text PowerShell would refuse — an unterminated string, here-string, comment or brace, a hash literal key without `=` (`@{u}`), `<` — is unparsed: at the top the line holds nothing, inside a payload the piece does. Nesting past 128 regions, or anything else that stops it, is unparsed too: it never throws.
- `shellTables.ts` (in `@jaira/shared`): the shell's tables, as data: `EMBEDDERS`, the utility → standard-tool tables `POSIX_UTILITIES`, `POWERSHELL_UTILITIES` (by the cmdlet's own name) and `CMD_UTILITIES` (`diff`, `stat`, `file`, `jq` and `sort` are `read_file`, and `sort -o` is `write_file`), `NO_REQUEST` per dialect, `NULL_DEVICES`, `DIRECTORY_CHANGERS`, `SCRIPT_INTERPRETERS` (with PowerShell's `Invoke-Item`, `Import-Module`, `Add-Type`, and `Invoke-Command`/`Start-Job -FilePath`, whose flags `POWERSHELL_INTERPRETERS` reads as PowerShell's), `SCRIPT_RUNNERS` and `SCRIPT_EXTENSIONS`. `POWERSHELL_ALIASES` is Windows PowerShell 5.1's alias table; `POWERSHELL_REDEFINERS` are the cmdlets that point a name elsewhere (`Set-Alias`, `Invoke-History`); `POWERSHELL_HARMLESS_MEMBERS` are the members `ForEach-Object <name>` may name without calling code. An embedder is a `shell` (`sh -c`; for `cmd` and `powershell` every word after the line switch is the line, PowerShell's switches read in any case and cut short, `-File` not opened, `-EncodedCommand` in any spelling, `-Command -` and a line that is one variable unreadable, and Windows PowerShell's first plain word the line), a `prefix` (with `wsl`'s line in POSIX), PowerShell's `expression` (`Invoke-Expression`: a line it can read, else unreadable — handed a variable, a subexpression or the pipeline), `process` (`Start-Process`: the program and its argument list as a cmd line, its `-RedirectStandard*` files as redirects, itself a request when `-Verb RunAs` or `-Credential` starts it as someone else) or `block` (`Invoke-Command`, `Start-Job`, `Start-ThreadJob`: the script block, taken apart where it was written, and the cmdlet a request of its own on another machine), `find` or `git`. `HARMLESS_VARIABLES` with `isHarmlessVariable` are the variables a line may set without changing what a program runs (`CI`, `NO_COLOR`, `FORCE_COLOR`, `TZ`, `LANG`, `LANGUAGE`, `TERM`, `COLUMNS`, `LINES` and `LC_*`, and PowerShell's `$env:` spelling of them); `isShellLocalName` is a lower-case name, which no program's environment carries until it is exported; `VARIABLE_SETTERS` are the builtins that set one (`export`, `declare`, `typeset`, `local`, `readonly`, `read`, `printf -v`, and `hash -p`, which points a command elsewhere). `CONFIGURING_OPTIONS` are a program's own options that change what it runs (git's `-c`, `--config-env`, `--exec-path=`). `PACKAGE_SCRIPT_RUNNERS` says how `npm`, `pnpm` and `yarn` name a script: after `run`, as `test`/`start`, or — for pnpm and yarn — as a bare word that is not one of the manager's own commands; which of the manager's flags are quiet; whether words after the name are passed on; and the flags that pick where the script runs — npm's `-w`/`--workspace`, `-ws`/`--workspaces`, `--include-workspace-root`, `--prefix`/`-C`, `--if-present`; pnpm's `--filter`/`-F`, `-r`, `-w`/`--workspace-root`, `--include-workspace-root`, `-C`/`--dir`, `--if-present`, with the pick selectors it does not read (`...`, `^`, `[since]`) and its quiet flags that take a value; yarn's `--cwd`.
- `commandParts.ts` in runtime: `classifyRequest` names what a request is for: a standard tool on its paths or url, `script`, a command subject, or nothing — in the request's own dialect. A `code` request is `script`. A PowerShell cmdlet's parameters are read cut short (`-Pat` is `-Path`), an array is one argument, a `bound` value is its parameter's and never positional, a cmdlet has no subcommand (`install-module`, never `install-module pester`), and a command answers to its cmdlet's entry and to its alias's (`remove-item` or `rm` for `rm x`). `ForEach-Object` naming a member it may call (`% Delete`) is `script`; a redefiner, `Set-Variable PSDefaultParameterValues`, and an item set on the `env:` (unless harmless), `function:` or `alias:` drive are not vouched for; cmd's `set NAME=…` is as an assignment is, and cmd's `/x` switches are no places. A part that sets a variable which is not harmless — before its command, through an embedder, or with an exporting builtin whatever the name's case, or with a non-exporting one under an upper-case name — is one the parser cannot vouch for, and a variable-setting builtin that does is a request rather than nothing; so is a command given one of its `CONFIGURING_OPTIONS` before its subcommand. `packageScriptOf(command)` reads which script a package manager is asked to run, the words passed on to it, and where — a `--prefix`, the workspaces picked (`WorkspacePicks`: by name, name glob, path or parent folder; all; the root; exclusions), whether a picked package without the script is passed over — from npm's and pnpm's flags (npm's anywhere before `--`, pnpm's before the script's name) and yarn's `workspace <name>`, `workspaces run` and `workspaces foreach` (`-A`, `-R` read as every workspace, `--include`, `--exclude`), or `undefined` when it names no script or is given something this does not read. `shellPermissionSetOf` and `shellPermissionSetOfBlock` read a `Permission set` or a lowered block as the map a line is judged against — a block's `subjects` and `source`, which a run's block carries too since upstream passes a host's keys through; a block with no `subjects` has no map — and `lookUp(set, part, where)` answers for one part ([0023](../decisions/0023-overlays-and-scopes.md) §3.4): the lines from most specific to least — every command entry naming the program, most specific first (`matchCommandEntries`; `matchCommandEntry` is the first), then the part's own subject (its standard tool, or `script`), then for a plain command, or a `script` with no `script` line, `shell`, then `other`, then `ask`. A line with PLACES answers only where one of them matches what the part is about (`PartPlaces`, which the policy builds): the most specific matching place decides (`resolvePlaces`), several places take the strictest, and the places none matches go to the line's own mode — its `**` — or, where it has none, on down the lines, never to a guess; the answer names the place that decided. A file tool's part (`cat x`) does not fall to `shell`: it is `read_file`'s, then `other`'s. `answerOfLines` is the same walk over a chain handed in, answering nothing when no line speaks — the runner gate's. A `ShellPermissionSet` holds each line's own mode in `entries` and its other places in `places`. A flag an entry names matches the same word, a long flag with its value joined on (`--output` matches `--output=a.patch`), and a one-letter flag inside a cluster of short ones or with its value joined on (`-f` matches `-fu`, `-O` matches `-Ovim`); where an allowing and a refusing entry are equally specific, the refusing one wins.
- `packageScripts.ts`: what a package script runs. `scriptRunsOf(reader, call, dir)` finds the packages — the nearest `package.json` at or above the directory, the one a `--prefix` names, or, for picked workspaces, the members of the nearest root above that declares workspaces, each pick matched (`picomatch`) against a package's `name` or directory, globs included, the root among the candidates, exclusions taken out, and only exclusions meaning every member but those — and the lines each runs, `pre` script, script with the words passed on (`shellWord`), `post` script; `undefined` when a package, a pick, or a script not passed over cannot be found. `makeCallOf` (in `commandParts.ts`) reads a make line — `-C`, `-f`, `-j`, quiet flags, assignments, targets, `-n` — or `undefined` for a flag that changes what runs (`-t`, `--eval`, `-q`) or a `SHELL=`; `makeRunsOf` dry-runs it through the reader only when `makefileRunsCodeWhenRead` finds nothing GNU make runs or honours while reading (`$(shell …)`, `!=`, `$(file|guile|eval …)`, `+` recipe lines, `$(MAKE)`, `include`, a `SHELL` of its own), and `makeDryRunLines` reads the output as recipe lines. `filePackages` is the reader on disk, its `makeDryRun` a `make -n` with a five-second limit and make's own environment settings cleared, cached by the makefiles' modification times: a root's workspaces are `workspaces` in its `package.json` (yarn classic's `{ packages }` too) or `packages` in its `pnpm-workspace.yaml` (read with `yaml`), and `expandWorkspaces` globs each pattern's `package.json` with `tinyglobby`, `!pattern` taking back and `node_modules` never entered; a test hands a table.
- `commandRunners.ts` in shared: the command runners ([0007](../decisions/0007-permissionSets.md), amended 2026-09-26, later). `COMMAND_RUNNERS` lists them with the hint Settings draws and which ones elevate; `RUNNER_GROUP_SUBJECT` (`runner:*`), `runnerSubject`, `parseRunnerSubject`, `isCommandRunner` and `runnerModeOf` (its own line, else the group's, else none). A `runner:` line is the subject kind `runner`: parsed, warned about and dropped when it names no runner JaiRA knows, carried in `subjects` by lowering, read back by `permissionSetOfEnvironment`, and counted by `shellWithheld` as letting the shell do something.
- `commandParts.ts` in shared: the payload, `CommandApproval` and `CommandPart`, with `askingParts`, `entriesToRemember` and `chosenWidths`. `CommandApproval.permissionSet` names the permission set that judged the line: the reference a state names it by, or `inline`.
- `permissionSetEdit.ts` in shared: "add to the permission set" as text in, text out. `addToPermissionSetText` sets entries in a permission set map, replacing a value where it stands, only the `mode` of an entry written as an object, and adding a new subject as one line after the last; `overridePermissionSetText` writes a new file that starts from a lower layer's by an explicit root and refuses a bare `$`; `permissionSetTextFollows` and `describeAddition` read one.
- `policy.ts`: `decideCommand(policy, line, dialect, options)` judges every part of a line and keeps the strictest verdict, returning the parts beside it. The narrowing decides a line once, under the map the state's block carries, or under the permission set the policy was compiled for when the block carries none. Per part: a `.jaira/` path denies; then, unless `functions.shell.builtins` is off, the built-in denies for destructive git and a recursive delete of `.git` (`rm -r`, `Remove-Item -Recurse`, `rd /s`), then the built-in asks for push, merge, network programs and cmdlets (`Invoke-WebRequest`, `Invoke-RestMethod`, `Enter-PSSession`, `Invoke-Command` on another machine), publishing, installing (`Install-Module` and its kind too), deploying, `Start-Process` as another user, and credential paths, and otherwise `default`, which allows; then the permission set's answer, the stricter of the two kept, except that an entry naming the program replaces a built-in ask or the default — an entry that names a FUNCTION answers `function`, ranked between `allowed` and `asks`, and the part's `decidedBy.function` says which; a part the parser cannot vouch for asks at least; an answer remembered in `CommandGrants` settles a part that asks — at a place, where it was kept at one; and the executor's scope FLOOR answers for the part's place by the standard tool the part is. A part is about places of the kind each line names (`partPlacesOf`, §3.1): a file tool's line and `script`'s by the paths it names, else where it runs; a command line, `shell` and `runner:*` by where it runs — a package script's package (`scriptRunsOf`), so `"npm run build": { "packages/app": "allow" }` answers `npm run build -w packages/app` from the root — and every path it names; `git push` by the branches it pushes (`pushedBranchesOf`, `remote:branch`); a network program by its URL; `runner:ssh` by its host. A command line naming a part decides it outright, its script unread, only where it answers there. An asking part carries `where` — its place kind, the place, and the place widths an answer may be kept at (`placeWidthsOf`, its package found through the reader). `DecideCommandOptions.places` is what a place is resolved against — the project root and the named places — and is not moved for a script's lines. `CommandGrants` keeps answers by width and place (`remember(width, decision, place?)`, `rememberParts(…, place?)`, `answerFor(widths, placesOf?, options?)`), never by line: a placed allowance covers a part only where every place it is about lies there, a placed refusal at any one of them refuses, and a placeless answer covers the width everywhere. The RUNTIME layer ([0023](../decisions/0023-overlays-and-scopes.md) §2.6 step 4): an answer kept for this run settles a part that asks, and a refusal kept for this run also refuses a part a set ALLOWS (or hands a function) at a line no more specific than the width it was kept at — over `shell`, `other` or a standard tool's line, which are no width of the part, and over `git` where it was kept at `git`, never over `git status`'s own line, and never over a line the TOOLS layer set, which is newer still (`runtimeOutranks`); an allowance never lifts a refusal (invariant 28). Every part a set decided names the LAYER that set its line at its place (`decidedBy.layer`, §2.7, read with `layerOfLine` off `DecideCommandOptions.stack`); a remembered answer names `runtime`; and the approval carries the stack's ids newest first, `runtime` under `tools` where answers are kept (`CommandApproval.stack`, `approvalStackOf`). A block that still says `scopes` — a task pinned before 2026-11-02 — is refused for every call that names a place and every shell line before anything else reads it (`staleScopesDecision`, `STALE_SCOPES_REASON`: the task must be started again), and its old table is never read. `JairaPolicy` is `{ builtins?: boolean }` and nothing else, read off `functions.shell.builtins` by `projectPolicy(config)`. `compilePolicy(policy, options)` — with `options.stack`, the stack a turn's set was composed from — turns it into upstream `ExecPolicy`, folding the per-tool modes of `options.permission set` into `baseline.tools`: `shell`, `run_command` and six other command tool names get upstream's `smart` in the baseline (a state that declares no permission set is judged by it), a permission set's shell folds over it as `ask`, no other tool gets a mode or a default from the project, `show_artifact` gets a size-judging approver that nothing resolves to since the project policy's `tools` went, a path under `.jaira/` is denied, and `scopeOf` narrows each call by the executor floor, and by the call's own answer: for a command tool the line's own verdict — a deny always, an ask when a permission set is judging the line (a line a permission set judges is audited here, whatever it came to); for a direct call to a tool whose line has places, the call's answer at its place (`placeNarrowingFor` over the block's `places`, else the compiled-for set's), which tightens the loosest mode the gate was handed to the call's own (§3.10), keeps what answered against the input (`notePlaceAnswer`, so a refusal names the permission set rather than the floor), and notes a place's — or the `**`'s, or `other`'s — function (`noteFunctionCall`, `FunctionCall.place`). For any other call that is not a shell line, the narrowing notes against its input which function decides it, when its line (or `other`) names one in the block's `functions` (`functionCallOf`). `CompilePolicyOptions.worktree` is what `$WORKTREE` names; `$PROJECT` is `workspaceRoot`. The decision is kept against the call's input object, where the `smart` approver and `commandDecisionOf` find it again. `scopeOf.narrows(tool, block)` says, with no call in hand, whether the narrowing may tighten a tool — its line has places, the floor holds a tool that acts somewhere, or it is a command tool, an MCP tool, one that always asks, or under a block that still says `scopes` — which upstream's `ToolGate.modeOf` reads before calling an `allow` safe to pre-approve ([0023](../decisions/0023-overlays-and-scopes.md) ruling 17); `scopeNarrowingFor`, `placeNarrowingFor` and the narrowing `gateTools` composes say the same, and `mayNarrow(narrowing, tool, block)` reads it, a narrowing that does not say counting as one that may. `commandNarrowingOf` hands `gateTools` the line half alone. `policyCanEscalate` says whether a person could ever be asked. A part whose program is a command runner answers first to its GATE when the set has a runner line: a command line naming the program decides it outright and nothing inside is read; otherwise a part of kind `runner` (subject `runner:<program>`, widths it and `runner:*`, the program underlined) takes the runner line's verdict, or what was remembered at those widths, and a refused runner's inside — the requests within its span — is not judged; an allowed or asking one is looked inside. With no runner line, an opened runner that was not kept is no request, as before. With `packages` (the gate passes `filePackages`), a part that names a package script is replaced by the parts of the lines it runs in every package it runs in (`scriptRunsOf`), each judged in that package's directory and standing in the runner's span with the runner's text in `via`; four scripts deep, or unreadable, it stays `script`. `allowsCall(policy, permissionSet, name, args, dialect)` says whether a permission set lets one recorded call run with nobody asked — `true` only for `allow` — judging an agent's built-in as the standard tool it is (`declaredNative` in `agentTools.ts`; `Task` and `Agent` are `other`), a tool of an MCP server by its server's lines, and a shell line (a command string, or codex's argv joined) through `decideCommand`, package scripts read through the reader it is given; it answers `undefined` for a native no agent declares (`TodoWrite`), which no map holds. The app's `judgeReadOnly` asks it of the project's `chat/read-only` for the work summary.
- `approval.ts`: `ApprovalHub` parks an `ask` as an `ApprovalRequest`, which carries the decision's `parts` when the call was a shell line. `grants(taskId)` is the run's `CommandGrants`, emptied by `allow(taskId)`; `decide(requestId, decision, scope, remember, why, by, place)` stores the asking parts at the chosen widths — at `place` too, when one was chosen (§3.8), kept in `ApprovalReach.place` and read back by `rememberAgain` — and then answers upstream `once`, and keeps a `deny`'s `why` against the call's input, where `refusalOf(input)` finds it: upstream's own refusal says only "denied by permission policy". `approver({ taskId, functions })` is `withPermissionFunctions` over the park, so every host that parks approvals — the app's runs and turns, and a CLI run's terminal — asks the functions first and lets a line its parts allow through. A `deny` with `remember` is a refusal "for this run" ([0023](../decisions/0023-overlays-and-scopes.md) §4.4): kept at the widths (and place) like an allowance, and applied by the policy as the runtime layer. The app's `submitApproval` hands `place` through to `decide`.

The same file holds the operation field tables the authoring form and the operation schema read.
- `commandLog.ts`: `CommandLog.record`, `list` and `summary` over `command_log`. In `service.ts`, `startRun` passes `compilePolicy` an `onDecision` that writes one row per decision, and `scopeFloorOf` reads the floor.

It deliberately does not own:

- Resolving a mode through the ledger, and escalating: upstream `decideToolCall`, `PermissionLedger`, `withPermission` and `createToolGate` in `@declarative-ai/permissions`. Upstream still has profiles; nothing JaiRA lowers carries one, and the linter refuses an authored one.
- Building `disallowedTools`, `allowedTools` and the permission callback from the services an executor is handed: upstream `AgentExecutor` in `@declarative-ai/agents-api`.
- Parking an approval for a person and attaching the policy's reason: [interaction-hub](interaction-hub.md). The inbox channels: [inbox-channels](../contracts/inbox-channels.md).
- Expanding every other reference in a state, merging `environment` layers, and resolving a lowered `tools` list against the registry: upstream `@declarative-ai/hw`. It reads a non-array `tools` as a binding and refuses a map with `unrecognized binding form`, which is why lowering happens before it.
- The tools themselves: [host-tools](host-tools.md) and [host-tool-vocabulary](../contracts/host-tool-vocabulary.md).
- MCP servers — configuring them, detecting the ones other tools run, probing their tools, and handing them to claude and codex (whose bridge proxies them, so a call to one of their tools is gated there as ours are): [mcp-servers](mcp-servers.md). What it does to a call to one of their tools is here, and is the shell's program groups again: a permission set line `mcp__<server>__<tool>` for one tool, and a SERVER line `mcp__<server>` for every tool of it no line names, answered in that order and then by `other` (`mcpModeOf`). The lines lower into `permissions.tools` at their gate modes; `translatedGate` asks the gate about a tool with no line of its own by its server's name and notes the tool on the call's input; the narrowing judges the call as one part of kind `mcp` whose widths are the tool and its server (`decideMcpCall`), so the approver, "for this run" and "add to the permission set" — a TOOL line by default — serve it as they serve a shell part.
- Parsing `functions` and executor `scopes`: [project-config](project-config.md), with the shapes in [settings-json](../contracts/settings-json.md). Folding the compiled floor over every prompt call: `withSecurityFloor` in [executor-tree](executor-tree.md).
- Deleting `command_log` rows: [history-pruning](history-pruning.md) and [task-lifecycle](task-lifecycle.md).

## The unit is core logic behind the upstream permission seams, compiled once per run and once per turn

- Layer `core`. The runtime and shared files import upstream packages, `@jaira/shared` and `paths.ts` from [process-exec](process-exec.md), whose `dialectFor` picks the parser dialect by the same rule `interpreterFor` picks the shell, so the language judged is the language run. `commandLog.ts` is persistence code and the wiring is main-process code.
- Upstream seams: `ExecPolicy` with `baseline`, `smart` and `scopeOf`, and `Approver`, reach the engine on the services seam as `ctx.policy` and `ctx.approve`. `ScopeNarrowing` is the `scopeOf` callback. `ToolGate` is what a delegated agent's permission callback consults. `providerOptions.claudeCode.settings.permissions` carries `allow`, `ask` and `deny` rules to Claude Code. `ExecServices.tools`, `ExecServices.gate` and `ExecServices.policy` are what `withAgentPermissionSet` hands the agent executor copies of, and with `ExecServices.authored` — the state's resolved `permissions` block, host keys included, published by the engine with or without an approver (declarative-ai 3f5e5cc) — what it reads a run's permission set back from. Upstream `literalPermissions` passes every key it does not read through verbatim, so the gate's and the narrowing's `authored` carry `subjects`, `source` and `implementations` too.
- Boundary: Windows and WSL. A WSL project's commands are parsed as POSIX and a native Windows project's as PowerShell — JaiRA's `shell` and codex's `shell` run where the project runs. An agent's own shell runs in its own: Claude Code's `Bash` is POSIX and its `PowerShell` is PowerShell, wherever the project runs.
- Callers of the lowering: `browseSource`, the pre-run live load in `lifecycle.ts`, `digest.ts`, `views.ts` and the CLI's `run --root` and `--workflows` call `loadWorkflowBundle`. The built-in generated workflows still call `loadBundle`: sync lowers its own permission set with `lowerPermissionSet`, and changeset-review and conformance declare none.
- Callers: app `startRun` compiles the run's policy with `compileRunPolicy` and the audit through `policyAuditRow`, calls `grantAlwaysGrantedTools` and `policyCanEscalate`, and hands the prompt executor `securityFloorOf`. The CLI does the same for every run it starts (`run`, `task start`, `task move`, `changeset review`, `workflow check`), through `governRun`, with the audit only where the run has a task; its approver is the terminal or a reasoned refusal. App `chatPlan` and `chatStartPlan` call `readPermissionSets`, word `effective.permissions` with `matchPermissionSet` in the bucket `bucketOf` answers, and hand both to the composer in `available`. App `savePermissionSet` checks a bucket, a name and a map and writes `permission-sets/<bucket>/<name>.json` through `writeFile`, which refuses the `system` layer. App `runChatMessage`, `chatPlan`, `chatStartPlan`, `changeChatSettings` and a run's opening message (`overriddenBundle`) first follow the composer's STACK (`withChatStack` → `resolveChatPermissionStack` with the project's standing layers) into the one map it comes to, handing the policy the stack (`CompilePolicyOptions.stack`; the root state's lowered block carries it, `stateWithChatSettings`); the plan views word the composed set and hand back the composer's own settings. App `runChatMessage` then reads the message's settings into one `Permission set` with `permissionSetOfSettings`, compiles a policy with no audit and that permission set folded into its baseline, calls `planAgentTools` and `gateTools`, and publishes the permission set on the turn's services with `withPermissionSetService` when the message declared tools. A kept native's place rules are written by `withAgentPermissionSet` at the executor, for a turn as for a run. `agentPromptRoutes` in [model-routing](model-routing.md) wraps every agent route in `withAgentPermissionSet` with that agent's declaration; `registerAgentRuntimes` registers the two claude functions with `wrapExecutor: agentFunctionWrapper(CLAUDE_TOOLS, …)` and wraps the codex function in `holdAgentFunction`, as `registerGenericAgents` wraps every generic CLI function. The CLI registers `run_command`, calls `policyCanEscalate`, and passes `executeWorkflow` the policy and approver `governRun` builds.

## The audit has no run column, and nothing else here is stored

## Policy matches parsed intent, and an agent is held to its permission set where the route is known, both on purpose

- A verdict is decided over `ParsedCommand`s rather than a pattern over the raw line, so a flag in another position or a wrapper cannot change it; the cost is that a line the parser cannot model asks.
- A part is a request for a subject, never a member of a category. `git commit` and `rm` both write and deserve different answers, so there is no read, write or network class: a utility is the standard tool on its path, and everything else is its own name.
- The floor comes first, then the permission set. The permission set composes with the built-ins as the stricter of the two, so no permission set opens the floor. The one exception is an entry that names the program, which replaces a built-in ask or the default: those two stand in for a decision nobody had made, and naming the command is making it. `"shell": "allow"` names nothing, so it does not.
- There is no project rule list (2026-09-23). A command a project wants answered is a line under the `shell` tool of its permission sets, because a rule list beside the permission sets was a second place a command's answer lived, composed with the first by a rule — rules first, first match wins, a permission set may only tighten — that nobody reading one permission set could see. What stands above every permission set is the floor alone, and the project can turn it off (`functions.shell.builtins`) and do nothing else to it. The cost: a line no permission set judges — `run_command`'s, a state's that declares no permission set — answers to the built-ins alone, so what a project used to deny there with a rule now runs.
- The line's verdict is a narrowing, not only a `smart` verdict. Upstream hands a state's block to `scopeOf` and to nothing else, and a narrowing runs whatever mode the tool resolved to, so a remembered `shell: allow` cannot wave a later line's parts through. The cost is the decision kept in a `WeakMap` against the input object, which holds only while upstream passes that object through unchanged.
- The shell's entry is lowered as `ask` (it was upstream's `smart` until 2026-09-22). `deny` would refuse the `git status` the permission set allows, and `allow` would pre-approve a delegated agent's shell so that no line was judged; `ask` reaches the host with the line in hand every time, and the host's approver — `withPermissionFunctions` — lets through what the parts allow and puts the parts a function names to it. The cost is that the approver must be the wrapped one: a bare approver asks about every line.
- A function is a mode rather than a special word, because what decides a call per call is a program, and the person should be able to write it, configure it and have it ask them — which the approval prompt, being a function too, lets it do without being an approval itself. It is run through the engine as a one-state workflow so every callee kind the language has is one kind, and a callee that parks parks as a gate does. The one exception is a shell with no line left to judge: `deny` with nothing that allows, asks or defers a command is withheld, because a door only a conversation turn could see was shut stood open in a run and to codex.
- A run reads the state's block as a conversation turn does, because upstream hands it over whole. `literalPermissions` passes every key it does not read through verbatim, and the engine publishes the resolved block on `ExecServices.authored` beside the gate (declarative-ai 3f5e5cc). `subjects` merges per key of `permissions`, so a child's own replaces its parent's.
- `PERMISSION_SET_MARKERS` stay as the discriminator between a map and a state that declares no permission set, read off `ctx.authored`. An empty map and no declaration lower to the same block without them, and the two mean opposite things to an agent. They are still a pair, where one key would do, because every block lowered since the migration carries the pair, and a pinned snapshot's map would otherwise read as no declaration.
- A permission set is lowered before the engine rather than read by it. The engine owns reference expansion and `environment` merging and offers no hook between them, and it cannot be changed from this repository, so JaiRA resolves the one node it must rewrite with the engine's own exported resolver and hands over the shape the engine already takes. The cost is the inherited-`other` row above.
- A permission set inside a referenced block is lowered BESIDE the reference rather than by pasting the block in. Pasting would move every relative reference in the target (`./prompt.md`) to the state's file and change what it names; siblings of a `$ref` are the engine's own override, and its merge already makes a sibling `tools` list replace the target's map and sibling `permissions` win per key. The cost is that only `tools` and `permissions` are read off the target, by a small merge written to match the engine's.
- A CLI run is governed by the app's recipe, not a CLI one. `compileRunPolicy` and `securityFloorOf` are what `startRun` compiles, so a policy change reaches both hosts at once; what the CLI adds is only an approver. It has no answer that allows everything: a built-in ask is a question somebody should see, so the way past one unattended is to write the answer in the permission set that judged the line, or, where no permission set judges it, to turn the built-ins off, which the refusal names.
- An agent is held to its permission set by a wrapper around its executor rather than by the lowering or the chat wiring, because the native names are the agent's and which agent answers is not known until the route is. The removals travel on the two fields the upstream executor already reads to build `disallowedTools`, and a run's permission set is read back from `ctx.tools` and `ctx.authored`, so what an entry chose reaches the executor in a run as in a conversation turn. A claude agent reached as a function is held by the same wrapper, which upstream's function entry takes as `wrapExecutor`, because an ask rule is written into the op the entry builds and no wrapper of the function's `run` sees that op; codex and a generic CLI, whose holding reads the call's inputs, are held through `holdAgentFunction`.
- Codex is gated at its bridge rather than refused. It has no permission callback, but every call to one of our tools crosses the MCP bridge, and upstream puts it to the same gate claude's callback consults, with the same subject and input, before the tool runs. Codex is told to approve our tools on its side (`approval_mode = "approve"`), because a non-interactive `codex exec` has nobody to ask and cancels the call otherwise, and to treat the bridge as `required`, which makes it wait for the handshake instead of starting the turn without the tools. With ours served, the writing sandbox is how codex's own writers are displaced, so it opens only for a writer an entry keeps with `native`.
- A child that writes a permission set does not inherit its parent's implementation choices. A map is the whole statement of what a state holds and whose code serves it (decision 0007 §1); a child that wants its parent's permission set and more says so with `$ref` and siblings. Lowering writes `implementations` on every map so the engine's per-key merge replaces the parent's; `other` is still inherited where a child writes none, because a map cannot write "no `other`", and an unwritten one is the gate's last resort.
- The list form of `tools` and the old `permissions` modes are refused rather than read. They were read, with a list a grant rather than a fence, until every workflow had been migrated to a map (0007 step 7); after that the reader was code for a form nothing used, and a snapshot pinned before the migration is read as the new form, which is the row above.
- `gateTools` registers no profile table. What the tables existed for, an answer about a name nothing registered, is the permission set's `other` on the block the gate takes, and a map's `allow` now reaches the tool without asking.
- A line's places are judged per call, the gate handed the LOOSEST answer any place can give ([0023](../decisions/0023-overlays-and-scopes.md) §3.10). Upstream's narrowing only tightens, so a stricter baseline would refuse a call a place allows before anything saw where it was; the narrowing then brings every call down to its own answer. The cost is that a host that hands a gate no narrowing — none does — would judge a line at its loosest.
- A place map is lowered whole, in authored words, rather than as gate modes beside a `functions` entry per place: nothing upstream reads `places`, so it can say what an author said, a function by its name, and one key is the line. `tools` keeps the loosest mode and `subjects` the own mode for the readers that read only those.
- The state table `permissions.scopes` was moved onto lines and deleted (§3.7), and an executor's `scopes` stay a separate floor (§7.2). A table alone was a sandbox — what it did not name was refused — so the feature workflow's tables became `{ "**": "deny", "<folder>": "allow" }` on the tools they named, and `deny` on every other place-taking tool its set held (`glob`, `grep`, `edit`, `shell`, `web_fetch`, `show_artifact`), which is what the table answered for them.
