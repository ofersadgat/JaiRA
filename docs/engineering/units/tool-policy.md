# Tool policy

## The unit decides what a tool call may do and where, and leaves remembering and asking to others

- `command.ts`: `takeApart(line, dialect)` turns a line into the requests it is made of, in the `posix` or `powershell` dialect ([0007](../decisions/0007-toolsets.md) §4): every command, every redirect, and every piece it could not model, each with its span in the original line. It comes apart at `&&`, `||`, `;`, `&`, `|`, newlines, `( … )`, `{ … }`, `$( … )`, backticks and `<( … )`; a here-document's body is data; `if`, `then`, `do` and `!` lead a command without being one. Embedders are opened recursively, with spans kept in the original line through a per-character offset map: `sh -c`, `powershell -Command`, `eval`, `exec`, `find -exec`, `xargs`, `env`, `sudo`, `nohup`, `time`, `timeout`, `nice`, `watch`, `parallel`, `ssh`, `docker exec`, `git -c alias.…`, `git submodule foreach`, `npx`, `pnpm dlx`. It skips the value a `-C` or `-c` flag takes, as in `git -C <dir>`. `parseCommand` is the same walk reported as `ParsedCommand`s. A line it cannot model comes back `unparsed` with a reason, an unreadable payload comes back as a request of kind `unparsed` beside the rest, and it never throws.
- `shellTables.ts`: the shell's tables, as data: `EMBEDDERS`, the utility → standard-tool tables `POSIX_UTILITIES` and `POWERSHELL_UTILITIES`, `NO_REQUEST`, `NULL_DEVICES`, `SCRIPT_INTERPRETERS`, `SCRIPT_RUNNERS` and `SCRIPT_EXTENSIONS`.
- `commandParts.ts` in runtime: `classifyRequest` names what a request is for: a standard tool on its paths or url, `script`, a command subject, or nothing. `shellToolsetOf` and `shellToolsetOfBlock` read a `Toolset` or a lowered block as the map a line is judged against, and `lookUp` answers for one part: the most specific command entry naming the program, then the part's own subject, then `other`, then `ask`.
- `commandParts.ts` in shared: the payload, `CommandApproval` and `CommandPart`, with `askingParts`, `entriesToRemember` and `chosenWidths`. `CommandApproval.toolset` names the toolset that judged the line: the reference a state names it by, or `inline`.
- `toolsetEdit.ts` in shared: "add to the toolset" as text in, text out. `addToToolsetText` sets entries in a toolset map, replacing a value where it stands, only the `mode` of an entry written as an object, and adding a new subject as one line after the last; `overrideToolsetText` writes a new file that starts from a lower layer's by an explicit root and refuses a bare `$`; `toolsetTextFollows` and `describeAddition` read one.
- `policy.ts`: `decideCommand(policy, line, dialect, options)` judges every part of a line and keeps the strictest verdict, returning the parts beside it. Per part: a `.jaira/` path denies; then authored `rules` with the first match winning, then the built-in denies for destructive git and `rm -r .git`, then the built-in asks for push, merge, network programs, publishing, installing, deploying and credential paths, then `default`; then the toolset's answer, the stricter of the two kept, except that an entry naming the program replaces a built-in ask or the default; a part the parser cannot vouch for asks at least; an answer remembered in `CommandGrants` settles a part that asks; and a scope table answers for the part's place by the standard tool the part is. `CommandGrants` keeps answers by width, never by line. `compilePolicy(policy, options)` turns `JairaPolicy` into upstream `ExecPolicy`, folding the per-tool modes of `options.toolset` over the project's in `baseline.tools`: `bash`, `run_command` and six other command tool names get `smart` in the baseline, `show_artifact` and every tool authored `smart` get a size-judging approver, a path under `.jaira/` is denied, and `scopeOf` narrows each call by the executor floor and the calling state's `permissions.scopes`, and for a command tool also by the line's own verdict: a deny always, an ask when a toolset is judging the line. The decision is kept against the call's input object, where the `smart` approver and `commandDecisionOf` find it again. `commandNarrowingOf` hands `gateTools` the line half alone. `policyCanEscalate` says whether a person could ever be asked.
- `approval.ts`: `ApprovalHub` parks an `ask` as an `ApprovalRequest`, which carries the decision's `parts` when the call was a shell line. `grants(taskId)` is the run's `CommandGrants`, emptied by `allow(taskId)`; `decide(requestId, decision, scope, remember)` stores the asking parts at the chosen widths and then answers upstream `once`.
- `tools.ts`: `gateTools` wraps named registry tools and builds a `ToolGate` over one `PermissionLedger` for one conversation turn; it reads modes from a `Toolset`, the one it is handed or the one it folds from `names` and the legacy `authored` block, and writes the block the upstream gate takes from that map. `planAgentTools` takes a `Toolset`, or the list and implementations map it folds into one, and splits the offered tools into tools to inject, native names to ask about and native names to deny. `grantAlwaysGrantedTools` adds `show_artifact` to every prompt state of a run's resolved bundle. `profileRules` turns `TOOL_PROFILES` into upstream profile tables. `scopeNarrowingFor` and `commandSubjects` build the per-call narrowing, and `partScopeFor` answers for one part of a line by the standard tool it is. `compileClaudeScopeRules` and `claudePermissionSettings` compile a scope table into Claude Code permission rules. `createRunCommandFunction` builds `run_command`, which gates itself.
- `toolsets.ts` in shared: the toolset, the one map every reader of a grant and its modes consumes ([0007](../decisions/0007-toolsets.md) step 1). `Toolset` is `entries` (subject → `{kind, mode, implementation, offered}`), `other`, and a legacy `profile`. `parseToolset` reads the authored map and reports a bad mode as an error and an unknown tool name as a warning. `resolveToolsetDecl` follows a bare-string reference and `$ref` with sibling overrides through an injected reader, and names a cycle. `toolsetOfLegacy` folds the old list and `permissions` block into the same shape: a listed tool takes `permissions.tools[name] ?? default`, a mode on an ungranted tool is kept un-offered, and `default` becomes `other`. `offeredTools`, `toolModes`, `toolImplementations` and `shellSubjects` are what consumers read. `gateToolModes` is `toolModes` with the shell's entry as `smart`, which is how `bash` is lowered; its authored mode is carried in `subjects`, and `toolsetOfEnvironment` puts it back. `lowerStateToolsets` rewrites a map-form state into the `tools` list and `permissions` block the upstream engine takes, in a state's `environment`, its `operation` and each child mount's `environment`, and returns a state with no toolset as the same object. `toolsetOfSettings` reads a message's `toolset`, or the three fields the composer still writes.
- `toolsets.ts` in persistence: `loadWorkflowBundle` is `loadBundle` behind that lowering, used by the browser, the pre-run load, the digest, the state views and the CLI. `toolsetReader` resolves a toolset reference with upstream `resolveReference` and the bundle's own options, so `$/toolsets/<bucket>/<name>` searches `paths.roots` in order and the file reaches `onReferencedFile`. `listToolsets(roots)` lists `toolsets/<bucket>/<name>.json` across the layer roots, first root winning, buckets free to nest. `toolsetWriteTargets(paths, reference)` says which writable layers a line for a `$/toolsets/<bucket>/<name>` reference could be written into, whether the write creates an override and of which lower layer, and whether a nearer copy shadows it; `addToToolset` makes the write and refuses the built-in layer, a map with no file, a reference that is not layered, a YAML file and a file that is not a map.
- `toolVocabulary.ts`: `TOOL_SPECS`, the one table of logical tool names with category, `readOnly`, Claude native name, `pathArgs`, `urlArgs` and `alwaysGranted`, and the `read-only`, `plan` and `full` `TOOL_PROFILES` generated from `readOnly`.
- `scopes.ts`: glob matching and `resolveScope`, `resolveUrlScope`, `resolveScopes`, `scopeModeOf` and `layeredScopeMode`. The most specific glob that says anything about the tool decides, an unmatched place is denied, and a call about several places takes the strictest answer.
- `operationVocabulary.ts`: `PERMISSION_MODES`, `PERMISSION_PROFILES`, `PermissionsDecl` with the `subjects` and `implementations` keys lowering writes, `ChatSettings` with its optional `toolset`, `ToolImplementation`, and the composer's `PERMISSION_PRESETS` with `presetModes` and `presetOf`. The same file holds the operation field tables the authoring form and the operation schema read.
- `commandLog.ts`: `CommandLog.record`, `list` and `summary` over `command_log`. In `service.ts`, `startRun` passes `compilePolicy` an `onDecision` that writes one row per decision, and `scopeFloorOf` reads the floor.

It deliberately does not own:

- Resolving a mode through the ledger and profiles, and escalating: upstream `decideToolCall`, `PermissionLedger`, `withPermission` and `createToolGate` in `@declarative-ai/permissions`.
- Parking an approval for a person and attaching the policy's reason: [interaction-hub](interaction-hub.md). The inbox channels: [inbox-channels](../contracts/inbox-channels.md).
- Expanding every other reference in a state, merging `environment` layers, and resolving a lowered `tools` list against the registry: upstream `@declarative-ai/hw`. It reads a non-array `tools` as a binding and refuses a map with `unrecognized binding form`, which is why lowering happens before it.
- The tools themselves: [host-tools](host-tools.md) and [host-tool-vocabulary](../contracts/host-tool-vocabulary.md).
- Parsing `policy` and executor `scopes`: [project-config](project-config.md), with the shapes in [settings-json](../contracts/settings-json.md). Folding the compiled floor over every prompt call: `withSecurityFloor` in [executor-tree](executor-tree.md).
- Deleting `command_log` rows: [history-pruning](history-pruning.md) and [task-lifecycle](task-lifecycle.md).

## The unit is core logic behind the upstream permission seams, compiled once per run and once per turn

- Layer `core`. The runtime and shared files import upstream packages, `@jaira/shared` and `paths.ts` from [process-exec](process-exec.md), whose `dialectFor` picks the parser dialect by the same rule `interpreterFor` picks the shell, so the language judged is the language run. `commandLog.ts` is persistence code and the wiring is main-process code.
- Upstream seams: `ExecPolicy` with `baseline`, `smart` and `scopeOf`, and `Approver`, reach the engine on the services seam as `ctx.policy` and `ctx.approve`. `ScopeNarrowing` is the `scopeOf` callback. `ToolGate` is what a delegated agent's permission callback consults. `providerOptions.claudeCode.settings.permissions` carries `allow`, `ask` and `deny` rules to Claude Code.
- Boundary: Windows and WSL. A WSL project's commands are parsed as POSIX and a native Windows project's as PowerShell.
- Callers of the lowering: `browseSource`, the pre-run live load in `lifecycle.ts`, `digest.ts`, `views.ts` and the CLI's `run --root` and `--workflows` call `loadWorkflowBundle`. The built-in sync, changeset-review and conformance workflows are generated in the list form and still call `loadBundle`.
- Callers: app `startRun` compiles the run's policy with the floor, `workspaceRoot`, `askAboveBytes` and the audit, calls `grantAlwaysGrantedTools` and `policyCanEscalate`, and compiles the floor into Claude rules for the prompt executor. App `runChatMessage` reads the message's settings into one `Toolset` with `toolsetOfSettings`, compiles a policy with no audit and that toolset folded into its baseline, and calls `planAgentTools` and `gateTools`. `chatOperationOf` writes the ask and scope rules into a turn's `providerOptions`. The CLI registers `run_command` and calls `policyCanEscalate`, and passes no policy to `executeWorkflow`.

| A line's decision | written by the narrowing or the `smart` approver; read by the approver and `commandDecisionOf` | a `WeakMap` keyed by the call's input object | the approval hub reads it for `parts` |

## A conversation turn and a CLI run are governed far less than an app run, and the audit records only policy's side

| When | Behavior | Recovery | UX state |
| --- | --- | --- | --- |
| A line does not parse, or holds PowerShell `$(`, `@(`, a backtick or `iex`, a `case`, a `function`, an encoded command, or a program or subcommand decided at run time | `require_approval` with `command could not be parsed (<reason>)`, or a part decided by `parser`; no width is offered, so the answer cannot be remembered | the person decides | an approval for the raw line, or for the part |
| A line runs a program that embeds a command and is not in `EMBEDDERS` | the program is an ordinary command subject, and what it embeds is not seen | add it to the table, or leave `bash` and `other` strict | the hidden command answers to `bash` or `other` |
| A map-form toolset gives `bash` any mode | lowering writes `tools.bash: "smart"` and the authored mode to `subjects.bash`, so the gate reads the line and a part with no entry of its own falls to that mode | none needed | `"bash": "deny", "git status": "allow"` offers the shell and runs only `git status` |

## Migration 16 dropped the audit's run column, and nothing else here is stored

- `command_log.run_id` was dropped by migration 16; it does not roll back. Every other input is configuration or snapshot data read at each start or turn, so a policy change applies to the next start or message without migration.

## The one budget is the size above which a smart payload asks

- `askAboveBytes` defaults to 4194304, `DEFAULT_ASK_ABOVE_BYTES` in `packages/shared/src/config.ts`.

## Policy matches parsed intent and profile tables shadow upstream's, both on purpose

- A verdict is decided over `ParsedCommand`s rather than a pattern over the raw line, so a flag in another position or a wrapper cannot change it; the cost is that a line the parser cannot model asks.
- A part is a request for a subject, never a member of a category. `git commit` and `rm` both write and deserve different answers, so there is no read, write or network class: a utility is the standard tool on its path, and everything else is its own name.
- Rules and the floor come first, then the toolset. The toolset composes as the stricter of the two, so a state can tighten the project's policy and cannot widen it. The one exception is an entry that names the program, which replaces a built-in ask or the default: those two stand in for a decision nobody had made, and naming the command is making it. `"bash": "allow"` names nothing, so it does not.
- The line's verdict is a narrowing, not only a `smart` verdict. Upstream hands a state's block to `scopeOf` and to nothing else, and a narrowing runs whatever mode the tool resolved to, so a remembered `bash: allow` cannot wave a later line's parts through. The cost is the decision kept in a `WeakMap` against the input object, which holds only while upstream passes that object through unchanged.
- The shell's entry is lowered as `smart`. Any other mode would let upstream answer for the tool before the line was read: `deny` would refuse the `git status` the toolset allows, and `allow` would pre-approve a delegated agent's shell so that no line was judged.
- A toolset is lowered before the engine rather than read by it. The engine owns reference expansion and `environment` merging and offers no hook between them, and it cannot be changed from this repository, so JaiRA resolves the one node it must rewrite with the engine's own exported resolver and hands over the shape the engine already takes. The cost is the inherited-`other` row above.
- `gateTools` registers tables under upstream's own `read-only`, `plan` and `full` names, so an agent's built-ins get an answer from the profile rather than an escalation for want of a `readOnly` flag.
