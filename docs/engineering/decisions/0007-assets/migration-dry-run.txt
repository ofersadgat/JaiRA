refused, every one of them because of the shell, and each refusal names the consent that would go
on. The SECOND is the same run with both consents given, which migrates all 33.

WHAT THE CONSENTS MEAN, because they are the whole decision the person is being asked to make:

  unlisted-shell  The state never granted `bash`, and claude kept its own Bash, every line of it
                  put to a person. No map can hold a tool the list never granted, so the map takes
                  the shell away. TIGHTENS: the state loses a shell it never asked for.

  shell-judged    The state pinned the shell to a mode of its own, so every line was put to a
                  person. A map cannot say that in a RUN: its shell entry is the answer for any
                  other command on a line taken apart, and the engine hands the policy a state's
                  tools, default, other and scopes only — `permissions.subjects`, which the
                  authored mode travels in, never arrives. The line is judged by the project's
                  command policy instead. MAY LOOSEN: a line a person used to be asked about can
                  now run. That judgement is what decision 0007 §4 is FOR, but it is a change, so
                  it is said yes to rather than assumed.

In this root the two coincide: each of the 12 refused blocks both never granted the shell AND had
every line asked about, so `--accept unlisted-shell` alone settles all 12 — the shell is taken
away, and there are then no lines left to judge. The second pass below passes both anyway.
