The permission editor, round 3: levels, kinds, and the mapping in Settings

dark

What changed since round 2. Four of your notes, and the engine as it is now.

• Three levels you can tell apart. A resource, an access, and a tool were all plain table rows. Here a resource is a band (tinted, an edge in its kind's colour, a tile, bold), an access is a pill on a thread hanging from it, and a tool is a dim monospaced line on a second thread. Design 1 puts this next to two other treatments; the rest use it.

• A resource has several kinds of place, and every kind must allow. Decision 0023 §3.1a, committed today: a process has a program, an owner and a machine, and what a call does to it is an action. A line writes a map per kind, and a call takes the strictest of its kinds' answers. So one access row holds chips of several kinds: node session this machine force. A pid is read back to its program and owner before the gate asks; the --scope=session flag lines are gone, now owner rules.

• A tool can touch several resources. open_app is about a window's program, the file it opens and the link it opens: Programs · Control, Files · Open, Sites · Open. It's listed under all three and allowed only where all three allow.

• The mapping lives in Settings, on the Tools page, as a section beside Permission sets. Built-in tools come mapped; an MCP tool can be mapped by naming the argument that holds its place. With the new kinds, power and read_clipboard map to Machine, so Other tools shrinks to the tools that touch nothing: search, the task and skill tools, and unmapped MCP tools.

Three ways to tell the levels apart

The same slice in three treatments: Files opened, its Read access opened into tools, Sites still condensed. Each one makes the three levels differ in more than one way, so they read apart even at a glance.
A, bands and threads (used in 2–6): a resource is a tinted band with its kind's edge and tile; an access is a coloured pill on a thread; a tool is a dim monospaced line on a finer thread, dashed between tools. Shape, colour, indent, height and type all change at each level.
B, solid headers: a resource is a solid header bar, like a spreadsheet's group. Strongest split between resources, but heavy with several open, and condensed rows full of chips sit badly on solid colour.
C, weight and indent: no colour, a heavy rule above each resource, a dash before each access, smaller monospaced tools. Quietest, but the closest to what you found hard to read.

An access of several kinds

Programs · Control opened. Condensed, an access row holds chips of every kind it has, told apart by icon and colour. Opened, its third level can be by kind (shown) or by tool (5): a lane per kind, each holding that kind's map. The rule is the engine's: every kind must allow, and the call takes the strictest. The strip below the board works it through on three real calls. A pid is read back to its program and owner first; one nobody can read takes the strictest answer anywhere on the line.

A tool under several resources

open_app touches three resources, so the Resources view lists it under each: Programs · Control (the window it focuses or closes), Files · Open (the file it opens) and Sites · Open (the link). Under each, its tool line shows only that resource's chips. A + 2 marker says it's elsewhere too; hovering it shows the whole tool and the rule: a call is allowed only where every resource it touches allows. Opening src/a.ts in Code asks: Files · Open allows src/a.ts, but Programs · Control asks about a window of the user's. Moving a chip on one resource never changes the others. Tools of one access that disagree still make a MIXED chip, as in round 2.

The Tools view, a tool's resources

The Tools side, in the same three levels: a category is the band, a tool is the pill, and its third level is the resources it touches, a lane each. open_app is opened into its three resources, each with its own chips. shell touches Files · Run, and its commands are also judged as System tools: ps as list_processes, kill as stop_process, npm -g as install_software. The lane lists those as links rather than copying their chips. An MCP tool mapped in Settings shows where its mapping came from.

Settings: the tool mapping

Where the mapping lives: Settings → Tools, as a section right after Permission sets, so what a set answers and what each tool touches are read in one place. Like the rest of Tools it is layered: built in, Shared, Just you, a project. A row per tool, and the resources it touches as chips, each naming what it's read from: the tool's kinds of place (path, program · owner · action) or an argument for an MCP tool. A tool can have several. Built-in tools come mapped; you can move one to another access (here list_windows was moved from See to Screen), and Reset puts it back. Tools that touch nothing are collected at the top, each with Map. A second tab, Resources, lists the resources and their accesses, where you'd add an access such as Repositories · Admin.

Settings: mapping an MCP tool

Map… on github·search_code opens a drawer. Pick the resources it touches from the accesses Settings knows; for each, say where the place comes from: an argument, or a pattern of arguments like {owner}/{repo}. The drawer tries it on the tool's last call so you see the place it would have been judged at. Leave the place empty and the tool is judged by the resource's anywhere answer only. The bottom says what changes on the board: the tool leaves Other tools and takes its answers from the resource it joined.
